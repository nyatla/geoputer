# 動作モード別メモリ構成設計

2026-10-30。GPSロガー・USBストレージ・Wi-Fi管理の固定資源を、起動時に選択する一つのunionへ統合する。Wi-Fi管理モードも同じ最上位のモード領域へ配置する。

## 1. 配置

Applicationは共通資源とApplicationModeMemoryを所有する。後者はBootModeResourcesの一つのunionであり、GPS一式・USB一式・Wi-Fi一式を重ねて配置する。App用とStorage用を別々の最大サイズで予約せず、モード全体の合計が大きい方を予約する。

```text
Application
├ 共通資源
│ ├ App通知キュー・同期結果キュー・SyncClient
│ ├ UiTask・表示資源・UiData
│ ├ StorageTask・SPI・設定ストア・返送領域
│ └ 共通の画面遷移・ファイル一覧要求・再起動状態
└ ApplicationModeMemory : union
  ├ GPS : GpsApplicationResources
  │ ├ AppGpsResources
  │ │ └ GpsTask・記録制御・地図制御・地名検索・アラート・起動確認
  │ └ StorageGpsResources
  │   └ 区域キャッシュ64 KiB・地図／索引作業96 KiB・選択情報・検索器・ログ記録
  ├ USB : UsbApplicationResources
    ├ AppUsbResources
    │ └ エクスポート用ファイル一覧の画面状態
    └ StorageUsbResources
      └ USB媒体制御・一覧Reader作業領域・エクスポート状態
  └ Wi-Fi : WifiApplicationResources
    ├ Appの画面所有状態
    └ StorageのWebServer・固定FIL・転送4 KiB・保存先パス・通信状態
```

固定領域は「共通領域＋max(GPS一式, USB一式, Wi-Fi一式)＋タグとアラインメント」となる。unionは一つであり、各メンバーの先頭アドレスは等しい。未使用側の余白が自動でシステムヒープへ戻る方式ではない。Wi-Fi起動時に限り、下記の明示的な登録を行う。

## 2. 構築と寿命

mainの静的Application構築では、共通の管理オブジェクトと空のモード領域だけを構築する。NVSの起動モードを読んだ後、Application::beginの先頭でGPS・USB・Wi-Fiのいずれかをplacement newにより一度だけ構築する。大きな一時オブジェクトをタスクのスタックへ作らず、その予約領域へ直接構築する。

共通キューの初期化とUI・Storage・GPSタスクの開始はモード選択後に行う。GPSモードでは既存の4タスク・5キュー、USB・Wi-FiモードではGPSタスクとキューを開始しない3タスク・4キューという実行構成を維持する。

同じモードの資源選択は再構築せず、別モードへの選択は拒否する。実行中にunionを切り替えるAPIは設けず、モード変更は従来どおり保存して再起動する。アプリケーションを破棄する場合は、タスクと借用が終了した後にStorageTaskが有効メンバーだけを破棄する。StorageObserverが生きている間にファイル等を閉じ、最上位unionの後続デストラクタでは二重に破棄しない。通常の実機運転中にはこの破棄を行わない。

## 3. 所有権とアクセス

メモリ予約の所有者はApplicationとする。Appはそのモードのappメンバーを、StorageTaskはstorageメンバーだけを操作する。StorageTaskは同じApplicationModeMemoryへの参照を保持し、自身の配列を別途持たない。UIの画像所有権とApp経由の借用返却は変更しない。

GPSモード内では、選択情報は引き続きStorageの領域に一つだけ存在し、PlaceLookupが参照する。地図セッション・FIL・Reader・区域キャッシュの参照先はモード構築後に固定される。地図と索引作業、ログ読出しと地図ジョブの内側の排他配置も維持する。

USBの共通処理からGPS専用メンバーへ触れないよう、画面遷移・通知振分け・一覧読出し・終了準備を分離する。USB一覧のReaderにはGPSのLogWriterを渡さず、記録セッションの待機処理も行わない。GPS・地図・データセットに関する不適切な通知やUI要求は、USB側の入口で無視または拒否する。

## 4. 動的確保と今後の拡張

この変更でモード資源を取得するためのmalloc/newは追加しない。placement newは既存の固定領域でオブジェクトの寿命を開始するだけである。RTOSのタスク・キュー、外部ライブラリ内部の初期化確保、既存USBエクスポーターの遅延確保は従来の扱いを維持する。

[Wi-Fi管理モード](19_Wi-Fi管理モード仕様.md)のWifiApplicationResourcesを同じ最上位unionへ追加した。第1段階ではWebファイル管理の固定資源を配置し、後続の展開・索引保守もその内側へ配置する。Wi-Fi用のアプリ資源には、WebServer、DNS制御、SD専用の固定FIL一つ、4 KiBの転送バッファ、パス・進捗・認証制御を含む。転送ファイル全体や編集全文を端末に確保せず、本文はブラウザーが保持する。ディレクトリ走査などの小さい一時値は局所スタックを使う。

Wi-Fiを構築した後、同じ最上位unionの未使用の末尾を16バイト境界へ内側に整列し、ESP-IDFのheap_caps_add_regionへ一度だけ登録する。登録前に、全範囲が静的Applicationの.bss内に収まることを確認する。生存するWi-Fiオブジェクト、モードタグ、登録済みフラグは含めない。これによりGPSの大きな固定予約の余白を、Wi-Fi起動中にシステムの動的確保へ利用できる。

これは無線専用の独立アロケーターではなく、システムヒープへの追加領域である。Wi-FiドライバーやTCP/IPの動的確保をアプリ側からすべて固定化したことを意味せず、追加領域の利用者も無線に限定しない。GPS・USB起動時には登録しない。登録後はモード領域を破棄しても再構築を禁止し、再起動を必須にする。通常運転中のApplicationは静的寿命であり、追加領域を返却しない。

Wi-Fiドライバーの内部ヒープは実機の初期化前後で計測する。リンカが示す固定RAMと、実行時に追加ヒープとして利用可能になった容量は重複するため、単純加算で総使用量を計算しない。GPS資源を静的領域から動的領域へ移すことは、この整理の前提にしない。
