# 動作モード別メモリ構成設計

2026-10-30。GPSロガー、USBストレージ、Wi-Fi管理は、専用のApp・UIタスク・Storageタスクを持つ独立したアプリケーションとする。

## 1. 最上位の配置

mainの静的ApplicationRuntimeは、ApplicationMemoryと選択管理だけを所有する。ApplicationMemoryはBootModeResourcesを使い、アプリ全体を一つのunionへ配置する。

```text
ApplicationRuntime
└ ApplicationMemory : union＋選択タグ・余白登録ラッチ
  ├ GpsApplication
  │ ├ 通知8件／同期結果1件のキュー、同期管理、App状態
  │ ├ GpsUiTask：描画バッファ、地図表示／受信画像、画面状態、音声
  │ ├ GpsStorageTask：設定、固定FIL、地名・地図・ログ・索引・アラート
  │ └ GpsTask：受信キュー、UART、測位状態
  ├ UsbApplication
  │ ├ USB専用の通知／結果キュー、同期管理、App状態
  │ ├ UsbUiTask：USB画面モデル、描画バッファ
  │ └ UsbStorageTask：媒体公開、固定FIL、一覧／エクスポート作業
  └ WifiApplication
    ├ Wi-Fi専用の通知／結果キュー、同期管理、App状態
    ├ WifiUiTask：接続画面モデル、描画バッファ、QR行列
    └ WifiStorageTask：WebServer、DNS、固定FIL、転送4 KiB
```

App、UI、Storageを共通の具象タスクとしてunionの外側へ残さない。固定予約は「max(GpsApplication, UsbApplication, WifiApplication)＋タグと整列」となる。USB・Wi-Fiの型にはGPS受信状態、地図2枚、区域キャッシュ、GPS記録バッファ、区域アラートを含めない。

同じ実行基盤・フォント・アイコン・ファイル処理は共用する。UIの小さいモデル基盤と描画部品、物理キー変換、SPI初期化も部品として共用し、アプリごとの状態とタスクの所有者は分離する。SDKのグローバル変数や初期化内部ヒープは、このunionに含めたアプリ固定予約とは別に扱う。

## 2. 構築と寿命

静的初期化時にはアプリ本体を構築しない。LoRaの安全停止、起動フラグ読出し、USB MSCの事前登録を経て、ApplicationRuntime::beginが選択アプリ一つを固定領域へ直接構築する。そのアプリが自分のキューとタスクを開始する。App処理はArduinoのloopTask上で実行する。

GPSはApp・UI・Storage・GPSの4タスク／5キュー、USB・Wi-Fiは専用App・UI・Storageの3タスク／4キューとする。各アプリのサブタスクの受信キューは一つずつである。別モードのタスクは開始しない。

稼働中のアプリを別のunionメンバーへ置き換えるAPIは設けない。モード変更はNVS保存後の再起動で行う。アプリ全体の所有者はApplicationRuntimeだけとし、Storageが最上位unionを破棄する経路は持たない。ホスト試験等で破棄する場合も、先にタスク・コールバック・借用を停止し、有効メンバーだけを一度破棄する。実機の通常運転では静的寿命を維持する。

## 3. タスク内部の排他領域と通信

並行動作するUIとStorageの領域は重ねない。GPS UIの表示画像とStorageへ貸出中の受信画像も別領域とする。GPS Storageの区域キャッシュ64 KiBと地図／索引作業96 KiBは独立した固定領域のまま保持する。地図／索引作業、および地図ジョブ／ログ読出しには既存の内側のunionを使用する。

USB StorageはLogReaderとUsbExportWorkを専用variantへ配置し、GPS用MapBuildJobを持ち込まない。媒体制御とコールバック排他状態、固定FILは、この作業variantと別に保持する。変換器は既存どおり必要時に確保し、ファイルを閉じられない場合には保持して再公開を待つ。

通知・同期応答・UI内容はGPS、USB、Wi-Fi別の型とする。共用するのはMessageHeaderと小さい列挙型、Task／Queue／BasicSyncClientの基盤である。USB・Wi-FiのキューへGPSの最大payloadを予約しない。

Appが発行した同期要求は、タイムアウトしても結果取得まで待機状態を保持する。通常通知は数量8、同期結果は数量1の別キューとし、状態通知が満杯なら最新状態を保持して再送する。Wi-Fiの終了・認証再生成は引き続き投機的な制御とする。GPSのUI→App→Storageの型付きメモリ借用と、ログ共有RAMリングの排他規則は維持する。

## 4. Wi-Fiの余白登録

WifiApplication全体を構築した後、最上位unionの未使用末尾だけを16バイト境界へ内側に整列し、heap_caps_add_regionへ一度だけ登録する。範囲が静的.bss内に収まることを確認する。

WifiApplicationが所有する全タスク、キュー、状態、バッファと、外側の選択タグ・登録ラッチは範囲に含めない。登録後はメンバーを破棄しても再構築できず、再起動を必須とする。GPS・USBでは登録しない。

これはシステムヒープへの追加であり、Wi-Fi専用アロケーターではない。ドライバーやTCP/IP内部の確保を固定化したことを意味しない。リンカ上の固定予約と、この予約を再利用する追加ヒープを二重に加算して使用量を評価しない。

## 5. サイズ検収

ApplicationRuntime全体は変更前のApplication 219,528 B以下、固定RAM全体は281,908 B以下を検収条件とする。コードにも最上位予約の上限検査を置く。比較対象は旧部分union単体ではなく、従来の外側管理を含めたアプリ全体とする。

実機向けELFとホスト試験の結果は[アプリ別タスクと固定領域の検証](検証/アプリ別タスクと固定領域の検証.md)へ記録する。タスクスタック、外部ライブラリ内部ヒープ、USB変換器の確保を全廃する作業は本変更の範囲外とする。
