# ReverseGeoputer 地図表示モジュール設計

文書状態: 実装仕様 0.2（ホスト検証・実機向けビルド対象）
更新日: 2026-10-24

対象画面: [地図画面](画面・操作/place-view/README.md)。本書は実装したモジュールの責務、データ形式、所有権と連携を定義する。4キーで地図を表示する。今回の実装では既存の128×128キャッシュと統合しない。

## 1. 分離方針

画像処理と境界画像の形式を`application/map/`へ独立させる。このモジュールはStorageTask、SD、Galuchat、FreeRTOS、GPSのスナップショット、M5GFXに依存しない。入力は区域コードのラスタと座標変換情報、出力は色に依存しない境界画像とする。

モジュールの分離とタスクの分離は別に扱う。初版では画像処理もStorageタスクのジョブから呼び出す。ファイルや区域コードの大きな配列をAppへ転送せず、既存の4タスク・5キューを維持する。画像処理モジュール自身はタスク・キュー・通知・ファイルハンドルを持たない。

## 2. モジュール構成

```text
application/
  map/
    MapTypes.h               座標・矩形・区域コード・処理結果
    ViewportTransform.h      地図中心、表示範囲、格子と画素の変換
    MapFrameReceiver.h      UIの受信・検証・表示画像の交換
    BoundaryImage.h          2bit境界画像とその参照
    BoundaryExtractor.h      区域コードからの境界抽出
  task/storage/
    MapBuildJob.h            要求受付後の読出し・変換・結果保持
    galuchat/
      MapSource.h/.cpp       選択中データセットと既存Readerへの接続
  task/ui/
    UiRenderer.cpp          drawMapによる境界画像・マーカー・地名・縮尺の表示
  MapView.cpp               Appの更新周期・行転送・取消制御
```

純粋な画像モジュールとMapBuildJobはヘッダー内に実装する。既存の`DiskIndexedMapReader`や地名検索を削除・置換するものではない。

| モジュール | 担当する処理 | 依存先 |
|---|---|---|
| ViewportTransform | 中心と縮尺から必要な格子範囲を計算。画素と地理座標を変換 | MapTypesのみ |
| BoundaryImage | 画像の確保、画素の取得・設定、行単位のコピー | 標準C++とMapTypes |
| BoundaryExtractor | 区域コードのサンプリング、隣接比較、境界種別の出力 | 上記の純粋なデータ型 |
| MapSource | 元ファイル・保存索引・格子単位の取得、区域コードの矩形読出し、中心区域の地名取得 | 既存のGaluchat読出し・辞書・データセット管理 |
| MapBuildJob | 処理段階とバッファの所有、進捗・成否、取消、完成画像の保持 | MapSourceと画像モジュール |
| Application | 要求の発行、更新タイミング、世代管理、StorageとUIの中継 | 既存のタスク通信 |
| MapRenderer | UIの色へ変換して描画。現在地、地名、北、縮尺と共通ステータスを重ねる | BoundaryImageの読取参照と既存UI |

MapSourceはStorageタスク専用とする。Readerの取得・破棄、媒体排他、SDランプ、索引の異常判定はこの側で行い、画像モジュールに持ち込まない。RGの状態と既存の地名検索キャッシュの状態を、地図の画像更新状態と混同しない。

## 3. 共通データと座標

`RegionCode`は`uint32_t`とし、0は区域なしを表す。現在のコード範囲検査を継続し、大きな値を切り詰めない。

`RasterView`は、区域コード配列への読取専用参照、格子上の原点、幅・高さ、行間隔と配列長を持つ。原点は西端・南端、xは東向き、yは北向きとする。ポインタは同一タスク内の呼出しにだけ使用し、タスク間キューへ入れない。

planViewportは中心の経緯度、元データの経度・緯度方向の格子単位、作業メモリ上限と表示寸法を受け取る。経度方向の格子1個を表示1画素へ対応させる。初版は北が上の固定縮尺とする。回転・ズーム・手動スクロールは初版に含めない。

`ViewportTransform`はこれらを受けて`ViewportPlan`を作る。Planは表示画素から元の格子への写像、必要な読出し矩形、中心の格子位置とスケール表示用の距離を持つ。緯度に応じて縦横の距離差を補正し、画像と500m等の目盛りに同じ換算を使う。

表示画像の原点は左上、xは右向き、yは下向きとする。240×101の画像内の中心は(120,50)とし、画面上はy=18を加えて(120,68)へ置く。座標の反転・丸めはViewportTransformへ集約する。配列参照は事前に検証した整数格子位置へ限定し、各画素で別の丸め規則を使用しない。

## 4. 境界画像の保持形式

BoundaryImageは1画素2bit、行優先の形式とする。RGB565やM5GFXのパレット番号は格納しない。

| 値 | 意味 | 初版の表示色 |
|---:|---|---|
| 0 | 背景 | 黒 |
| 1 | 周辺区域の境界 | 灰色 |
| 2 | 現在区域の境界 | 白 |
| 3 | 予約。初版では出力しない | 入力時に不正として扱う |

1バイトに左から4画素を格納し、x=0の画素をbit7〜6、x=1をbit5〜4へ置く。行間隔は`ceil(width / 4)`バイトとし、各行末の未使用bitは0とする。画像長は`stride * height`である。240×101では60×101＝6,060バイトとなる。

BoundaryImageはバッファを所有する。読出し側はconst BoundaryImage参照を使い、転送時はMapFrameReceiverが行範囲・順序・予約値・行末の未使用bitを検証する。サイズ計算のオーバーフローと容量不足を拒否する。大きな配列を関数のスタックへ置かず、地図画面の利用期間に必要な容量を確保する。

画像自体には現在地マーカー、文字、方角、縮尺、記録状態、ランプを描かない。これらはUIが重ねるため、時計や電池の更新で境界を再計算する必要はない。

## 5. 境界抽出のインタフェース

画像モジュールの主要操作は次のとおりとする。

```cpp
Error planViewport(double latitude, double longitude, int unit_x, int unit_y,
                   size_t max_bytes, ViewportPlan&, int width = 240, int height = 101);
Error buildBoundaryRows(const RasterView&, const ViewportPlan&, RegionCode current,
                        unsigned first, unsigned rows, BoundaryImage&);
```

planViewportはファイルを読まず、必要な格子矩形と座標変換を計算する。buildBoundaryRowsは指定行だけを出力する。処理段階・次の行・キャンセル状態は呼出し側のMapBuildJobが保持し、画像モジュールにはタスク実行の状態を持たせない。

各表示画素で区域コードを最近傍サンプリングし、右・下の表示画素と異なる場合に境界を出す。画像の右端・下端には仮想的な外枠を作らない。比較するいずれかの区域コードが非0のcurrent_regionなら現在区域の境界とし、それ以外は周辺境界とする。中心の区域が0なら白線は生成しない。領域外との境界もこの規則で処理する。

行の分割位置でも次の行のコードを参照し、継ぎ目を作らない。入力ラスタは、指定行とその隣接比較でPlanが要求する全サンプル位置を含む必要がある。範囲外の入力を黒として補って正常完了にせず、呼出し条件の不正として返す。将来の縮小時に細い区域を残す処理はサンプリング方式の追加として扱い、保持形式は維持する。

画像モジュールの結果は成功、入力不正、未対応の表示範囲、容量不足、メモリ不足などに限定する。SDエラーやデータセットの状態へ直接変換しない。BoundaryExtractorはバッファを追加確保せず、渡された入力と出力だけを使う。

## 6. バッファの所有と初版の読出し方式

| データ | 所有者 | 生存期間 |
|---|---|---|
| 区域コードの入力ラスタ | Storage側のMapSource／読出しセッション | 読出し開始から境界変換の終了まで |
| 生成中・完成後の境界画像1枚 | Storage側のMapBuildJob | 要求受付からRelease／取消まで |
| 表示中の境界画像 | UI | 地図画面の表示中 |
| 受信中の次の境界画像 | UI | 次画像の受信開始から切替／取消まで |
| 要求と画像のメタデータ | App、Storage、UIの値コピー | 対応する要求・表示の期間 |

Appは画像全体や区域コード配列を常駐保持せず、最大8行のTransferを1個だけ中継用に保持する。Storageの同期結果をこのバッファへコピーしてからUIを呼び、両方の同期関数の転送フレームを重ねてスタックに保持しない。StorageとUIのバッファは共有しない。

初版はMapSourceが必要な矩形を一度読み、そのラスタを画像モジュールへ渡す方式とする。表示処理の行分割ごとにDiskIndexedMapReader::readRectを呼ばない。同APIは呼出しごとに索引を走査するため、単純な細分化で索引・ブロックを繰り返し読むことを避ける。

区域コードの入力ラスタは地図専用に確保し、Live Place用128×128キャッシュとは共有しない。地図の読出し・失敗・取消・離脱で既存キャッシュやWordbook LRUを無効化せず、RGの状態も変更しない。MapSourceは独立したReaderを生成し、中心区域の地名も別経路で取得する。境界変換の完了時に入力ラスタを解放し、完成画像だけを保持する。今回の実装では128キャッシュとの統合・用途切替は行わない。

画像モジュールは全画面の入力保持を要求する形式に依存しない。将来、MapSourceに重複読出しを増やさない分割取得経路を追加した場合も、必要な比較用サンプルを含む参照を渡すことで境界画像の形式とUIを維持できる。

初版の設定値はConfig.hへ集約する。表示寸法と転送上限はMapTypes.hの定数とする。

| 項目 | 初期値・上限 |
|---|---:|
| 表示幅・高さ | 240×101 |
| 区域コード作業バッファ上限 | 96KiB |
| 画像変換の1ステップ | 8行 |
| 画像転送の1回 | 最大8行＝480バイト |

画面例の格子解像度・縮尺では元ラスタは約240×83×4＝79,680バイトとなる。実際の確保量はPlanで計算し、上限を超える表示範囲を拒否する。境界画像はStorage1枚とUI2枚で18,180バイトを要する。既存の128キャッシュ64KiBも保持する。これらにReaderのバッファとオブジェクト、転送用の値コピーが加わるため、6,060バイトだけを地図機能全体の必要メモリとはしない。初版の縮尺と作業上限は実機の最大空きブロック・最低空きヒープ・所要時間を測って確定する。

## 7. メタデータとタスク通信

画像に対応するFrameInfoは、要求ID、画面世代、データセット世代、画像寸法、中心のFix識別子と座標、中心区域コード、地名、縮尺情報を持つ。同じIDの画像とメタデータを1つの完成結果として扱う。UIは新しいGPS座標だけを古い地図の中心へ置いて位置が一致したように表示しない。

タスク間通信は既存方式を使い、次の操作を使用する。同期要求の発行元はAppだけである。

| 方向 | 操作 | 意味 |
|---|---|---|
| App→Storage、同期 | RequestMap | 生成要求の受付。生成完了は待たない |
| Storage→App、投機的通知 | MapCompleted（FrameInfo.errorで成否） | 完成したフレーム情報または失敗を通知。画像全体は入れない |
| App→Storage、同期 | ReadMapRows | 完成結果から最大8行を値コピーで取得 |
| App→UI、同期 | BeginMapFrame／WriteMapRows／CommitMapFrame | 受信開始、行のコピー、完全な画像への表示切替を受け付ける |
| App→Storage、同期 | ReleaseMap | 転送済み完成画像を解放する |
| App→Storage、同期 | CancelMap | 不要になった要求の取消を受け付ける |

画像全体をUiDataやAppNotificationへ埋め込まない。行データも別の転送キューには置かず、既存のAppReturnQueueとUIQueueを通る要求・結果のpayloadとして扱う。追加後のメッセージサイズとキュー全体のRAM使用量を計測する。

同期結果のタイムアウトは要求の取消ではない。結果取得まで待機状態を維持し、新しい同期要求を送らない既存の契約を守る。ReleaseやCancelも、先行する同期要求の戻り値を回収した後に発行する。

Storageは同時に1つの地図ジョブを保持し、完成画像をReleaseまで変更しない。通知がキューへ入らなければ同じ最終結果を保持して再試行する。処理段階はIdle、Reading、Rendering、Completeとし、失敗・取消時は不要な入力と出力を解放する。変換のステップ間では受信処理と必要なログ保存を行う。読出し時間そのものの上限は実測し、64件のログバッファとの共存を確認する。

UIは受信中の画像を描かず、全行と寸法・世代を検証したCommitだけで表示中画像を入れ替える。AppはUIのCommit受付成功を確認した後にStorageの完成画像をReleaseする。画面離脱、データセット切替、失敗時は古い要求の取消・解放を行い、遅れて届いた通知や行データを表示へ戻さない。

## 8. 更新と異常時の扱い

地図の中心は完成画像のFixと一致させる。Appは5秒以上の間隔で、新しいGPSサンプルがある場合に再生成を要求する。受付が競合した場合や失敗後は1秒以上待って再試行する。画像モジュールにタイマーを持たせない。消灯中は要求を取り消し、新規読出しを行わない。再生成中は対応する中心情報とともに前の完成画像を維持し、更新中と分かる表示を加える。初版では地図の平行移動や回転で追従を近似する処理を含めない。

未測位・データセット未選択・SD利用不能・地図範囲外はApp／UIが表示状態へ反映する。区域コード0は地図領域外や区域なしとして扱い、ファイル破損と同一視しない。画像バッファの確保失敗だけで正常なデータセットの選択を解除しない。地図専用の読出し異常はMAP READ ERRORとして地図画面へ表示し、前の完成画像があれば保持する。地図専用経路の失敗だけで選択や既存キャッシュを変更しない。GPS表示・記録は継続する。原データ範囲外でコード0を取得した場合はNO REGIONとして正常に表示する。

## 9. 検証

純粋な画像処理・行転送・キー操作のホスト試験と、N03／estat実データでの独立性試験を行った。完成前の表示抑止、旧世代の拒否、既存キャッシュの保持も確認した。実装した描画コードから原寸画像を生成し、正常・更新・測位喪失・読出しエラーの4場面でパレットとRGB565の全画素一致を確認した。

試験コマンド・容量・実機未確認項目は[独立境界地図の検証](検証/独立境界地図の検証.md)に記録する。実機の連続記録・空きヒープ・所要時間は書込み後の確認項目とし、ホスト時間を実機性能として扱わない。

縮小表示の帯読出し試作は[縮小帯読出しの実機比較](検証/縮小帯読出しの実機比較.md)に記録する。通常の固定縮尺の実装とは分けて測定し、初版の仕様は維持する。
