# LoRa位置ブロードキャスト機能要件案

調査日：2026-10-30。実装前の検討案であり、送信を有効化する承認済み仕様ではない。現行の「LoRaを使用しない」というコンセプトと、起動時のLoRa停止処理は本書によって変更しない。

## 1. 目的と初期範囲

現在のGPS座標を、同じ無線設定を使用する受信機へ直接ブロードキャストする。Raw LoRaの一方向通信とし、メッシュ中継・経路探索・ACK・LoRaWANへのJoinは行わない。受信機が存在しなくても送信でき、配信成功は保証しない。初期実装は地上での携帯利用を対象とする。

GPSロギングとは独立して開始・停止できる。座標の送信にGaluchatの地図・Wordbook・SDカードは必要としない。地名、住所、ログ閲覧中の測位点は送信せず、AppがGPSタスクから受け取った実際の現在地を使用する。

初期状態は送信OFFとする。地域・チャネル・周期は保存するが、送信開始状態は保存せず、再起動後は利用者が改めて開始する。USBストレージモードでは送信しない。外付けGPS構成など、対応するLoRaハードウェアがない場合は開始操作を無効にする。

## 2. 既存ネットワークとの識別

無線層には標準のPrivate LoRa用Sync Wordを使い、アプリケーション層には独自識別子 `RGPB`、版番号、種別、長さを設ける。受信側は全条件とCRCを確認してから位置データとして扱う。SX1262のPrivate Sync Wordは16 bit表記で `0x1424`、Public LoRa用は `0x3444` である。ライブラリによって8 bitの `0x12` / `0x34` を受け取るため、HALで表記を統一する。[Semtech SX126x資料](https://m5stack-doc.oss-cn-shenzhen.aliyuncs.com/1177/DS_SX1261_2_V2-2.pdf)

Private Sync Wordは他のRaw LoRaシステムも使うため、本システムだけの識別子にはならない。LoRaWANとはパケット構造が異なり、メッシュシステムとは独自ヘッダーで区別する。同じ周波数での電波干渉を防ぐ仕組みとは分けて扱う。

最初の版は平文の位置公開とする。端末IDやCRCは認証・暗号化にはならず、なりすましを防げない。受信機側での自動制御や真正性が必要になる場合は、別途認証方式を設計する。

## 3. ハードウェアと認証で分ける地域プロファイル

周波数だけを国別に切り替える方式にはしない。国・適用制度・認証された基板とアンテナ・無線パラメータ・送信時間制御を、一組のプロファイルとしてROMに収録する。利用者が任意の周波数や出力を書き込む設定は設けない。

| 米国 | FCC ID 2AN3WM5CAPLORA1262。Digital Transmission System、Part15C、903.0〜914.9 MHz、伝導出力0.008 W | 902〜928 MHz全体や、任意の915 MHz設定が許可されたとみなさない。試験された帯域幅・変調設定を確認する |
| EU向け | CE証明書B2602033。LoRa 868〜868.6 MHz、9.69 dBm ERP、外部アンテナ3.54 dBi | 一般的なEU868の最大出力や869 MHz帯の設定を流用しない。使用国の制度と、当該製品の適合条件の両方を満たす |

製品ページの付属アンテナは3 dBi表記で、各証明書の記載値とは一致しない。手元の基板・アンテナと、証明書および詳細試験条件との対応を確認する。上表だけでは、新しいファームウェアの全設定が認証の範囲内にあると確定できない。

### 3.2 国別の制度上の扱い

| 対象 | 設計方針 |
| --- | --- |
| 日本 | 初期対応の対象とする。認証書の8チャネル、922.0 / 922.2 / 922.4 / 922.6 / 922.8 / 923.0 / 923.2 / 923.4 MHzから選ぶ。これは本機用の周波数リストで、ARIB共通のチャネル番号とはしない。認証条件に対応したBW・SF・出力・キャリアセンス・休止時間を確定してから送信を許可する |
| EU各国 | 868〜868.6 MHz内を候補とするが、各国の制度を確認して個別に有効化する。ERPと伝導出力を区別し、アンテナ利得を含めて制限する |
| 英国 | EUとは別プロファイルとする。IR2030の868.0〜868.6 MHzでは25 mW ERP、規定の干渉軽減手法または代替の占有率1%以下という条件がある。製品側のより低い認証条件も合わせて確認する |
| 米国 | まず公開FCC認証のDTS方式の詳細を確認する。125 kHz固定チャネルの日本・欧州向け設定は流用しない。独自FHSSは初期実装の対象外とする |
| カナダ・豪州・NZ・韓国など | 周波数が近くても米国設定を流用しない。国ごとの制度と本機の認証を確認するまで送信を無効とする |
| インド・中国など | 対象帯域とRF回路・アンテナの対応も確認する。433 / 470 MHz帯などは周波数設定の変更だけで対応できるとみなさない |

日本のARIB STD-T108にはキャリアセンスを要する方式と要しない方式があり、「日本では常に同じLBT条件」と固定しない。LoRaのCADはLoRa信号の検出機能なので、制度上求められるキャリアセンスの代用になると決めつけない。[ARIB STD-T108概要](https://www.arib.or.jp/kikaku/kikaku_tushin/desc/std-t108.html)

米国の47 CFR 15.247では、DTSの6 dB帯域幅は500 kHz以上が条件で、FHSSには別のホップ数・占有時間条件がある。LoRaの設定値「BW500」だけで、測定上の6 dB帯域幅条件を満たすと判断しない。[47 CFR 15.247](https://www.ecfr.gov/current/title-47/chapter-I/subchapter-A/part-15/subpart-C/section-15.247)

欧州のCEPT勧告は参照資料とし、実際の使用国の国内制度を確認する。LoRaWANのRegional Parametersは利用計画の参考にはなるが、国別の送信許可そのものにはしない。[CEPT ERC/REC 70-03](https://docdb.cept.org/document/845)、[英国IR2030・2026-10-23版](https://www.ofcom.org.uk/siteassets/resources/documents/spectrum/interface-requirements/ir-2030.pdf?v=426935)

### 3.3 プロファイルが保持する値

国コード、制度・認証の識別子と改訂、対応基板・アンテナ、中心周波数一覧、BW・SF・CR・プリアンブル長・Sync Word・IQ設定、伝導出力、ERP/EIRP上限を保持する。さらにキャリアセンスの要否と条件、1回の最大送信時間、必要な休止時間、占有率と集計窓、集計を共有する帯域、必要ならホッピング条件を保持する。

不明な条件はゼロや無制限で補わず、そのプロファイルを無効にする。国の選択は手動とし、GPSの座標から無断で切り替えない。GPS座標だけでは国の認証・機器条件を判断できない。

## 4. 送信内容の案

位置パケットは40バイト固定とし、すべての複数バイト整数をLittle Endianで符号化する。C++構造体の生メモリを送らず、明示的に読み書きする。無線のPHY CRCも有効にする。

| オフセット | バイト数 | 内容 |
| --- | ---: | --- |
| 0 | 4 | ASCII `RGPB` |
| 4 | 1 | 版番号：1 |
| 5 | 1 | 種別：1＝現在位置 |
| 6 | 1 | フラグ：bit0 UTC有効、bit1高度有効、bit2速度有効、bit3進行方位有効。上位4 bitは0 |
| 7 | 1 | 全体長：40 |
| 8 | 4 | 送信端末ID。初回生成して保存する32 bit値。世界での一意性は保証しない |
| 12 | 4 | 起動ごとのランダム値 `boot_nonce` |
| 16 | 4 | 起動内の送信シーケンス番号 |
| 20 | 4 | UTC Unix秒。うるう秒の表現はUnix時刻に合わせる |
| 24 | 4 | 緯度：符号付き、度×10^7 |
| 28 | 4 | 経度：符号付き、度×10^7 |
| 32 | 2 | 高度：符号付きm。GPSが出力する平均海面高度を使用 |
| 34 | 2 | 速度：符号なしcm/s |
| 36 | 2 | 進行方位：符号なし、度×100、0〜35999 |
| 38 | 2 | 先頭38バイトのCRC16-CCITT-FALSE。poly=0x1021、init=0xFFFF、非反転、xorout=0 |

任意項目が未取得または値域外なら、その値を0として対応フラグを落とす。緯度・経度は有効な測位結果を必須とする。受信側は長さ・版・予約bit・値域・CRCを検査する。重複判定には端末ID、boot_nonce、シーケンス番号を使う。

受信機は同じ地域・周波数・BW・SFなどの設定が必要になる。まず単一チャネルで受信できる評価機を別途用意し、ホスト用デコーダーも公開可能な形にする。

## 5. 周期と送信時間の管理

操作上の初期候補は30秒、60秒、120秒とする。起動後の初回時刻を分散し、以後も0〜3秒の正のランダム待ちを加える。受信確認がないため再送はしない。送信できなかった古い位置を列に貯めず、次回は最新の1件を使う。

FIX喪失、GPS停止、サンプル取得から5秒超過では送信を見送る。送信直前にもサンプルの鮮度を確認する。GPS時刻が無効でも位置が有効ならUTCフラグを落として送信できる。周期・待ち時間には単調増加時計を使い、GPS時刻の補正で連続送信しない。

送信許可の判定では、希望周期より地域プロファイルの制約を優先する。予定のTime-on-Airを送信前に計上し、上限に達する場合は待機する。チャネル変更で同じ帯域の占有率枠をリセットしない。テスト送信も計上する。再起動で占有率制限を回避できないよう、必要な履歴を保存するか、履歴不明時は保守的に待機する。保存方式は実装時にNVSの書換え頻度と合わせて決める。

40バイト、CR4/5、明示ヘッダー、PHY CRC有効、プリアンブル8の試算は次のとおり。これは設定の合法性や通信距離を示す値ではない。

| BW | SF | 1回の送信時間 | 30秒周期での占有率 | 仮に1%制約なら必要な平均間隔 |
| --- | ---: | ---: | ---: | ---: |
| 125 kHz | 7 | 82.176 ms | 0.274% | 8.218秒以上 |
| 125 kHz | 9 | 287.744 ms | 0.959% | 28.775秒以上 |
| 125 kHz | 10 | 534.528 ms | 1.782% | 53.453秒以上 |
| 125 kHz | 12 | 1974.272 ms | 6.581% | 197.428秒以上 |
| 500 kHz | 7 | 20.544 ms | 0.068% | 2.055秒以上 |

表の必要間隔は送信時間÷0.01を1 ms単位で切り上げた値であり、集計窓の端の判定、個別の連続送信上限、休止時間は別に満たす。計算は `Ts=2^SF/BW`、`Npayload=8+max(ceil((8PL-4SF+28+16CRC-20IH)/(4(SF-2DE)))*5,0)`、`ToA=(8+4.25+Npayload)*Ts` とする。PL=40、CRC=1、IH=0、Tsが16.384 ms以上ならDE=1。全SFの値は[占有時間試算CSV](検証/LoRa位置ブロードキャストの占有時間試算.csv)に収録する。

## 6. タスク構成と共有バス

RadioTaskを追加し、Appからの同期操作で設定・開始・停止を受け付ける。受付結果は速やかに返し、実際の送信完了・状態変化・異常はAppへの投機的通知とする。既存の「Appは通常通知キュー＋戻り値キュー、サブタスクは受信キュー1個」という方式を維持する。新しい戻り値キューは増やさない。

GPSタスクは無線処理を持たず、Appが現在位置をRadioTaskへ渡す。位置更新は最新1件への上書きとし、通常の操作メッセージを位置通知で詰まらせない。投機的通知の取りこぼしが送信制限の管理に影響しないよう、制限状態と実績はRadioTaskが所有する。UIはAppから状態を受け取る。

送信状態は `OFF → WAIT_FIX / WAIT_INTERVAL → CHANNEL_CHECK → TX → WAIT_INTERVAL` とし、占有率待ちは `WAIT_BUDGET`、異常は `ERROR` に分ける。キャリアセンス不要の認証方式ではCHANNEL_CHECKを省略できる。STOPは送信中でもタイムアウト付きで停止を完了させ、以後の送信を禁止する。

### 6.1 SDとLoRaのSPI共有

現実装ではStorageがFSPIを所有し、SDとLoRaが同じSCK G40・MOSI G14・MISO G39を使う。SDのCSはG12、LoRaのNSSはG5である。LoRaのNRSTはG3、IRQはG4、BUSYはG6。IRQはIOエキスパンダ経由ではない。[Cap LoRa-1262ピン配置](https://docs.m5stack.com/en/cap/Cap_LoRa-1262)

SPI資源はアプリケーション寿命の共有バスオブジェクトに整理し、StorageとRadioが借用する。各トランザクションでCS・クロック・モードを正しく設定する。既存のSPIライブラリ内部ロックだけに依存せず、FatFs・通常SD操作・USBのrawアクセスを含めた呼出し経路を確認する。

無線FIFOへの書込みとSetTxが済んだらバスを解放する。電波を送っている間はSX1262が自律動作するため、送信時間いっぱいSPIをロックしない。GPIO割込み処理ではSPI/I2Cを呼ばず、RadioTaskを起こしてからIRQを処理する。長いSD処理で送信開始が遅れた場合は、古い位置を送るより見送る。規定にキャリアセンス後の送信開始期限がある場合は、その短い区間を分割せず保護する。

### 6.2 RFスイッチと電力管理

CapのPI4IOE5V6408は内部I2C G8/G9にあり、P0がアンテナスイッチを制御する。これはLoRa電源の独立遮断スイッチではない。既存キーボード等と共有するI2Cアクセス、特にレジスタのRead-Modify-Write全体を排他制御する。

起動直後のNRST保持と、未使用時のcold sleepは維持する。送信が有効な間は、省電力「しない」では待機、「通常」「最大限」では送信間に復帰可能なsleepを使う候補とする。具体的なクロック・RFスイッチの復帰順は基板回路に合わせて検証する。連続受信はせず、必要なチャネル確認時だけ受信系を動作させる。

SetTxには必ず有限のハードウェアタイムアウトを設定する。異常時は送信を止め、停止できない場合はリセット保持へ戻す。本機でアンテナの脱落を検出できることは確認されていないため、ソフトウェアだけで送信中のアンテナ取外しを保護できるとはしない。メーカーはアンテナ未接続での給電を禁止している。利用者の送信開始操作だけで、このハードウェア上の注意を解消したとは扱わない。

## 7. UI・保存・メモリ

設定画面に「通信 → LoRa位置送信」を追加する案とする。国／機器プロファイル、認証内のチャネル、送信周期、端末IDを表示し、開始・停止と現在の待機理由を確認できるようにする。SF・出力などは確認済みプリセットに含め、任意設定は初期版に設けない。プロファイル不備や未対応機器は操作前にグレーアウトし、実行して初めて分かる無線初期化エラーは理由を表示する。

無線エラーは原則としてLoRa送信だけを停止し、GPS表示・ロガーを続行する。SPIの電気的異常などSDにも影響する場合は、既存のストレージ異常処理にも通知する。メイン画面への表示は送信有効状態と異常を最小限追加する案とし、現行SDアイコンに無線状態を混在させない。

設定はNVSの既存48バイト構造へ無理に詰め込まず、専用の版付きレコードを候補とする。プロファイルIDとその版も保存し、不明な版や破損は送信OFFとする。送信許可状態を自動復元しない。

送信用40バイト、最新座標、状態、送信制限の集計領域はRadio所有の固定領域とする。パケットごとのヒープ確保は行わない。RadioTaskのスタックは4〜6 KiBを初期見積りとし、キュー・OS管理領域・制限集計分を加えて実測する。これは容量を保証する値ではない。地図やUIの追加画像バッファは不要である。

ドライバ候補は[Semtech SX126x Driver](https://github.com/Lora-net/sx126x_driver)とし、版を固定してHALを実装する。実際に組み込む際にClear BSDライセンスを既存のライセンス画面へ追加する。Galuchat本体・SDKには変更を加える必要がない。

## 8. 実装の進め方と確定条件

1. 手元のU214・アンテナと公開認証の対応、JPのBW・SF・出力・キャリアセンス条件、ファームウェア変更の認証上の扱いを確認する。未確認の地域では送信を許可しない。
2. パケット形式、Time-on-Air、地域プロファイル、周期と制限判定をホスト上で確認する。時刻補正、再起動、チャネル変更による制限の回避が起きないことを含める。
3. SPI共有とPI4IOの排他を整備し、まず送信せずに初期化・停止・異常復帰を確認する。
4. 対応する受信機と適切なRF試験環境で、送信内容、時間、出力、停止、連続SDアクセスとの共存を確認する。認証条件に合う設定で実施する。
5. GPSのNO FIX・停止・USB切替・再起動を含むUI動作、スタック余裕、地図読込みとログ保存の時間変化を実測する。

初期版は日本向けの確認済みプロファイルと単純な位置送信に絞る。各国対応はテーブルの拡張で進められる構造にし、受信一覧・他端末の地図表示・暗号化・メッシュ化は別機能として扱う。現段階ではファームウェアの変更・書込み・電波送信を実施していない。
