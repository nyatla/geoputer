# 地名検索の固定バッファ化と直接出力

検証日: 2026-10-28

## 対象と変更

準備済みデータセットに対する通常のSearchPlaceを、UIから借りた固定領域と局所スタックで処理する。App・Storage・UIの要求と完了通知、貸出しID・世代の照合、画面離脱後の回収方式は維持した。索引形式とNVS形式は変更していない。

UI backの先頭にPlaceResult、その後にReaderの4 KiB、トークン番号とソート順のuint16_t配列各128件を置く。構成要素番号はuint32_tを維持する。1階層ずつ処理して配列を再利用し、128件を超える構成要素は容量エラーとする。異常時に動的領域へ切り替える経路は作らない。

各返却行は385 Bで、ASCII128文字と非ASCII64文字の混在をUTF-8最大4バイトで見込む。TMの幅から局所の出力位置を求め、必要な断片を返却行へ直接配置する。別の地名2行・断片文字列・vector<string>は保持しない。実際の表示結果は従来の画面幅でUTF-8境界を保って省略する。満杯になった行の後続検索は打ち切り、他方の行に必要な構成要素は続けて処理する。

小さい階層番号32件128 Bと、幅／出力位置128件256 Bは関数スコープのスタックに置く。TMのページ計画は従来と同じ32件の局所配列を使い、超過分は再走査する。Reader・FILを閉じてから次の本文を開くため、既存の単一4 KiBを共用する。データセット準備にもprepareIntoを用意し、大きな返却構造体の余分な一時コピーを除いた。

アプリ内GaluchatへreadCodeSetFromRootIntoとreadTokenIdsFromPageIntoを追加した。既存のvectorを返すAPIと逐次読出し経路は残す。core・SDKリポジトリへの同期は今回実施していない。

## ESP32ビルドのメモリ

この変更の直前に保存した通常ビルドELFと、変更後ELFを比較した。

| 項目 | 変更前 | 変更後 |
|---|---:|---:|
| 静的RAM | 253,612 B | 253,612 B |
| Flash | 1,243,833 B | 1,241,225 B |
| Application本体 | 217,432 B | 217,432 B |
| StorageTask本体 | 174,304 B | 174,304 B |
| UiData本体 | 1,392 B | 1,392 B |
| PlaceResult | 344 B | 992 B |
| PlaceReadWorkspace | 4,440 B | 5,600 B |
| UI back画像の容量 | 6,060 B | 6,060 B |

借用領域の使用量は1,160 B増えたが、既存のUI画像内に収まり、残りは460 Bとなる。画像配列やタスクのスタック設定は増やしていない。各64 Bの最終表示行を持つ16件LRUと通常表示スナップショットも拡張していない。

コンパイル結果の個別フレームは、新しい地名出力関数464 B、TM出力関数1,280 B、ページ計画関数256 B。従来のTM読出し関数は1,056 Bだった。StorageTask::completeJobは912→1,296 B、AppのprocessPlaceは384→1,056 Bとなった。後者はUIへの返却前に結果を回収する局所コピーを含む。これらは個別関数の値であり、呼出し全体のピークや実機ウォーターマークではない。実機の余裕は今回未計測。

## ホスト検証

以下を確認した。

- N03・estatの実データで、通常検索とUI借用検索の結果・キャッシュ動作・要求情報が一致。UI借用の7検索はいずれもC++ newの確保0回・要求0 B。準備を終えてから計数し、正常な検索だけを対象とした。
- N03の324点でコード面キャッシュと直接検索が一致し、既存の地名・書式・エラー・データセット切替試験が成功。
- 最大32階層の人工データで、直接出力の2行が従来の全地名取得＋書式展開と一致。空文字・順序変更・同じ構成要素の反復・%%を含む書式を確認。
- stdio／FatFsで、1階層80・128トークンの成功、129トークンの容量拒否とガード領域・Reader/FIL借用返却を確認。長い構成要素をTIの最初に配置し、TMの32件を超えるページ計画も検証。
- スペインの実Wordbookにある65・67・80トークンの構成要素で、追加APIの番号列が既存APIと一致。
- 返却領域が先頭であること、作業域との非重複、表示幅での省略、UTF-8途中切断の防止、行末余白の消去、画面切替・遅延通知時の所有権を確認。
- 通常ホスト試験、Appの記録・画面遷移試験、Galuchatの逐次／矩形／ブロック／RAW経路の互換試験が成功。ESP32 cardputer-advビルドが成功。

主なランナーはrun_native.py、run_logger_app.py、run_wordbook_phases.py、run_place_files.py、run_borrowed_place_files.py、run_galuchat_ranges.py。

初期準備のINI解析・検証、索引保守、借用を指定しない互換経路、異常時の例外生成には動的確保が残る。1階層ずつ処理するため索引や同じページの再読込みはあり、処理時間のベンチマークは今回省略した。実機への書込みは実施していない。
