# データセット事前索引生成の検証

後続の実機測定ではN03・estatそれぞれの生成時間と索引検証時間を分離した。[データセット索引の生成・検証時間](データセット索引の生成・検証時間.md)を参照。以下は生成経路を実装した時点の検証記録である。

更新日: 2026-10-21

対象は[事前索引ファイル仕様](../11_データセット事前索引ファイル仕様.md)の生成・適用経路である。通常起動・検索で生成ファイルを利用する経路は、この検証の対象に含めない。

## 1. 実装と操作

設定→動作設定→データセットで候補と地名用言語を選び、「適用して再起動」を確定すると、Storageが`/dataset/NN/_mapindex.tmp`を生成する。同じ番号・言語の再適用でも作り直す。ログは停止済みで、RAM未保存分とセッション閉鎖が完了している必要がある。F1メンテナンスからも同じ経路を使用する。

GLCの全ブロック境界とWordbookのTI00最上位・TT00ページ・TM00ページを収録する。生成した索引の構造・CRCと元ファイルの識別情報を検証し、同期・閉鎖後に`_mapindex.dat`へ公開する。続けてNVS設定を保存し、番号・言語が変わった場合だけ再起動する。変更のない再適用ではキャッシュを更新して明示再検証する。

生成中のUIは従来の適用中表示を維持し、SDランプの通知を継続する。進捗率・残り時間は未実装。シリアルには`[DATASET INDEX] generating`と、結果・所要ミリ秒を出力する。

## 2. ホスト試験

C++17の警告をエラーとして扱い、UBSanと標準ライブラリの境界検査を有効にして実行した。実データは作業用ディレクトリへコピーし、原本は変更しない。

| 試験 | 結果 |
|---|---|
| 統計区高精細版から生成、全索引位置の別Pythonパーサーによる照合 | 成功 |
| ファイル全体のサイズ・末尾CRC・GLCH/GW00のCRC・ファイル名CRC | 一致 |
| TI00の非バイト境界、depth=1、payload_bits=0の子走査 | 成功 |
| TM00の同じトークン長の連続ページ | 成功 |
| RAW・RAWS・LZSSの混在と、追加APIの単回利用・GI01末尾検査 | 成功 |
| チャンク長16,383 / 16,384 / 16,386バイトの対象判定 | 仕様どおり |
| 64KiBを超えたブロックの末尾での群分割 | 仕様どおり |
| 適用前に既存索引がある／ない場合のNVS保存失敗 | 旧索引を復元／新規索引を除去 |
| 書込み・fsync・fclose・公開renameの障害注入 | 設定保存を呼ばず、旧正式索引を保持 |
| 復元renameの障害と、その後の公開失敗・再適用 | 復元失敗を区別し、退避を保持。明示再生成で回復 |
| 生成中の元ファイル更新、GLC・Wordbookの途中EOF | 生成失敗。旧正式索引と選択を維持 |
| CRCを再計算した不正件数・領域長・予約値・ビット位置 | 構造検査で拒否 |
| 通常UI・設定・GPS・ログ・USBの既存ホスト試験 | 成功 |
| 従来Galuchat逐次Readerの読出しトレースと矩形APIの互換性 | 一致 |
| 実N03データの324点のキャッシュ／従来Point比較と地名復元 | 一致 |

統計区の生成結果は20,148バイト。162チャンク、404ブロック群、TI00 47件、TT00 778件、TM00 2件となり、仕様の試算と一致した。複数言語は同時収録せず、適用する1言語分を生成する。

再実行コマンドは次のとおり。

```sh
python3 tests/run_dataset_index.py <map.wgsmapset.glc> <names.giswordbook>
python3 tests/run_native.py
python3 tests/run_galuchat_ranges.py
python3 tests/run_place_files.py <N03.wgsmapset.glc> <N03.giswordbook>
```

## 3. ファームウェアとメモリ

PlatformIOの`cardputer-adv`環境でビルドに成功した。静的RAMは77,536バイト、Flashは1,151,273バイト。ファイルI/Oは実機では既存のFatFsドライブ番号を使用し、ホストでは同じ操作を標準ファイルへ適用する。入力と出力のファイルオブジェクトはヒープ上に1個ずつ確保し、各4KiBバッファと、最大1500件×8バイトのGLCH座標列を生成中だけ保持する。全ブロック・WordbookページをRAM配列へ展開しない。

FatFsの大きなFILをStorageのスタックに置かない構成とした。静的RAMのビルド表示を実行時の空きヒープやスタック残量と混同しない。生成中の実機ヒープ・スタック残量、SD所要時間、生成中のUI操作性は未計測である。

## 4. 残る実装と確認

通常起動と検索は従来のRAM索引・Readerを使用する。保存索引の逐次利用、索引欠落・不正時の起動チェック、起動時RAM索引生成の廃止は後続であり、本変更だけでは検索性能は変わらない。Core・SDK本体は変更していない。

実機への書込みと、実SDでの適用→生成→設定保存→再起動の確認は今回行っていない。FAT renameとNVS保存をまたぐ電源断の原子性は保証しない。電源断残存ファイルは自動採用しない。実機でのSD取り外し・電源断試験も未実施である。
