# メモリ削減の実装と検証

検証日: 2026-10-16

## 1. 対象と実装

[メモリ使用量レビュー](メモリ使用量レビュー.md)のうち、UIの16色化、SDのVFS予約枠削減、タスク通信型の分離を実装した。着手時のリポジトリ基準は`1d7371c`。既存の`third_party/licenses/upstream-3.txt`の変更は作業前から存在し、本変更では編集していない。コミットは作成していない。

設定値は`application/Config.h`へまとめる。

| 設定 | 現在値 | 意味 |
|---|---:|---|
| UiColorDepth | 4 | 16色パレット。16はRGB565の参照描画 |
| SdMaxOpenFiles | 3 | 同時に2 Readerを開く地図初期化へ1枠の余裕を確保 |
| MaxDatasetChunks | 1500 | データセットの最大チャンク数 |

UIはUiCanvasがRGB565色をパレット番号へ変換する。現在の9色、240×135の解像度、フォント、整数座標、一括転送を維持する。個々のフォントピクセルも同じ変換を通す。登録していない色を黙って別の色へ変換せず、色を追加する場合はパレットへ明示的に登録する。

全キューに使っていたTaskMessageは、UiRequest / GpsRequest / StorageRequest / AppNotification / ReturnMessageへ分離した。共通の16バイト封筒は維持し、GPS要求は引数を持たない。キュー数・件数、通知と同期結果の分離、結果取得のタイムアウト後も同じ結果を必ず回収する契約、キュー満杯時に完成済み結果を保持する規則は変更していない。

タスクスタック、128×128の32bit区域コード画像、1500チャンク上限、16件の地名LRU、64件のログ受付リング、10件のログ読出しは同じ容量を維持する。FatFsを含むフレームワークの再構築やFILの配置変更は行っていない。

## 2. ビルドと型サイズ

PlatformIOの`cardputer-adv`環境でビルドが成功し、警告・エラーはなかった。Xtensa GDBでESP32向けELFの型サイズを読み、起動ログの`[MEMORY]`でも同じ値を確認した。

| 型・領域 | 削減前 | 削減後 |
|---|---:|---:|
| UI要求1件 | 1056 B | 1056 B |
| GPS要求1件 | 1056 B | 16 B |
| Storage要求1件 | 1056 B | 144 B |
| App通常通知1件 | 1056 B | 664 B |
| 同期戻り値1件 | 1056 B | 280 B |
| 通常通知キュー8件・制御領域込み | 8544 B | 5408 B |
| 戻り値キュー1件・制御領域込み | 1152 B | 376 B |
| UIキュー1件・制御領域込み | 1152 B | 1152 B |
| GPSキュー1件・制御領域込み | 1152 B | 104 B |
| Storageキュー1件・制御領域込み | 1152 B | 240 B |

静的RAMは8592 B（約8.4 KiB）減少した。Applicationオブジェクト、全キュー、結果保持領域は包含関係があるため、各行を重ねて加算しない。

UiCanvasの画像本体は64802 Bから16201 Bとなり、追加のパレットは48 Bとなる。アロケータ等を除いた削減見込みは48553 B（約47.4 KiB）。SDのVFS枠5→3の見込みは8274 B（約8.1 KiB）である。

## 3. ホスト試験

`python3 tests/run_native.py`が成功した。既存の同期タイムアウト・遅延戻り値・要求ID照合・UI操作・GPS・設定・ログ保存と閲覧の試験を用途別の型へ接続した。追加試験では、最大のStorage要求の末尾まで値が保たれること、8件の通知が満杯でも同期結果を独立して送れること、10件すべてのバイナリレコードが通知キューで欠けないことを確認した。

描画用のホストアダプタはパレット番号とRGB565値を区別し、番号へ変換していない描画色をエラーにする。プレビュー生成では同じ製品Rendererを4bitと16bitで実行し、出力RGB画像をバイト単位で比較する。

- Settings: 日英各11画面。全設定候補の配置とフォントピクセル、ライセンスの既存フレーム一致も確認した。
- MENU・GPS Logger・ログ閲覧: 日英各15画面。
- データセット警告: 日英の上限超過・メモリ不足の4画面。
- Live Place: 記録・一時停止・GPS/SDエラー・再構築・SD読書き等の8画面。

計64画面で4bit / 16bitの出力が一致し、既存のPNG132ファイルも変更前のRGBピクセルと一致した。画像サイズ・字形・色・レイアウトの変更は検出していない。ネイティブ試験とSettings・ログ閲覧・警告の描画試験ではUndefinedBehaviorSanitizerも有効にした。`git diff --check`は今回の変更対象で成功した。既存ライセンスファイルの改行差分は変更対象に含めない。

## 4. 実機確認

対象MAC `70:af:09:df:46:d0`のCardputer ADVへアプリ領域だけを書き込み、書込みデータのハッシュ照合が成功した。生成物は`.pio/build/cardputer-adv/firmware.bin`、保持用コピーは`.pio/memory-optimized-firmware.bin`。SHA-256は`8b4fcc4253d59fcb378e4c9c97c63afebe4b61234e00ec6900a5984d129d888b`とする。

30秒間の通常起動ログ`.pio/memory-optimized-boot.log`と抽出値`.pio/memory-optimized-results.json`を保持する。NVS復元、FAT32マウント、172チャンクのデータセット確認、Mesh KitのGPS測位、Live Placeへの移行、千葉県習志野市の地名取得が成功した。続けてリセットを行わない60秒間の観測を`.pio/memory-optimized-operations.log`に記録した。観測中の再起動・パニック・アサートは検出していない。

落ち着いた後の空きヒープは約124.6 KiBから約187.4 KiBへ増え、差は64344 B（約62.8 KiB）だった。最小空きは約179.3 KiB、最大連続領域は約172.0 KiBとなった。初回検索は約0.84秒で、後続のキャッシュヒットではファイルAPIのアクセス数が0のままである。測位位置がわずかに異なる近接矩形の各1回の参考比較であり、同一条件の反復ベンチマークとはしない。

起動直後と後続検索ではヒープ値に552 Bの差があり、値が落ち着いた後の複数回は191928 Bを維持した。用途ごとの理論削減量を足した値と実測差を同一視しない。実機でキーを使うメニュー・設定・ログ閲覧、SD保存失敗、フォーマット、上限超過・メモリ不足の注入は、この自動起動確認では実施していない。これらのUI・ログ処理はホスト試験の範囲と区別する。
