# メイン画面・ログ保存検証

本書は採用仕様1.1の実装に対する検証記録である。最新の画面と画像は[メインレイアウト1.3検証](メインレイアウト1.3検証.md)を参照する。以下の試験結果・ファームのハッシュは当時の記録として保持する。現在の保存実装と後続機能の範囲は[測位記録ファイル仕様11節](../07_測位記録ファイル仕様.md#11-容量実装範囲検証状況)に従う。固定入力による保存単体試験を、実GPSとキー操作による記録開始から停止までの通し確認として扱わない。

検証日: 2026-10-15  
対象: Cardputer ADV、PlatformIO espressif32 6.12.0、Arduino ESP32 2.0.17  

## 対象と実装

Live Placeの240×135ドットの採用レイアウト、RGの継続状態とSDの実I/O、GPSの日時・速度・方位・衛星・HDOP、電池残量、MENUとGPS Loggerの記録操作、64件RAMバッファの保存を対象とする。ログ閲覧・GNSS休止制御・長いGISの分割は対象外である。

## ホスト検証

`python3 tests/run_native.py`は-Wall / -Wextra / -Werror、UndefinedBehaviorSanitizer付きで成功した。従来のキュー・同期戻り値・NVS設定・フォント・ライセンス閲覧に加えて、次を確認した。

- 同一UTCのGGA / RMCから日時・速度・方位・高度・衛星・HDOPを統合し、次のepochへ旧メタデータを持ち越さない。
- F1は記録中の一時停止だけに使い、取消を初期選択した確認を経る。再開・停止はGPS Loggerで行う。左右キーで確認項目を変更しない。
- SDは短いアクセスを150ms表示し、長いI/Oは終了まで保持する。古いrevision、同一IDの更新、タイマー周回を扱う。GPS喪失で有効なRGと実行中のSD状態を消去しない。
- RAMへ64件受付後、65件目を拒否する。RAM受付でSDアクセスを通知しない。同じ最終sample_seqの再要求を重複保存しない。
- OSのファイルサイズ制限で部分書込みを発生させ、全64件を保持する。制限解除後は未確定範囲の同じ位置へ再試行し、512＋64×32バイトへ重複なく保存する。各レコードのCRCと座標・符号・単位・フラグを検証する。
- CRC32の既知ベクトル123456789は0xcbf43926となる。日時不明・うるう日・JST日付境界・同一秒の連番・同一session_idの上書き拒否を確認する。

実ファイル検証は`python3 tests/run_place_files.py <N03 MapSet> <同じSJIS WordBook>`で成功した。習志野市庁舎・皇居付近、324点の元の点検索との比較、キャッシュ境界・0・重なり・読込失敗と復旧を確認した。RGはヒット時に再点滅せず、WordBookの読出しだけでSDアクセスが発生することも確認した。

## 描画

`python3 tools/render_live_place_layout.py`は実装のUiRenderer / UiModel / PixelFont / Shinonomeを無改変でホスト実行する。10状態それぞれに240×135 pxと最近傍4倍画像を生成し、RG・SDの色と赤帯の範囲を画素値で検証した。旧画像を再作成せず、Live PlaceのPNGはこの20枚だけとする。入力値は配置確認用であり、実機の現在値やGNSS実測ではない。

## 実機検証

初回の一時試験イメージは、setupのローカル変数にLogWriterを置いたため起動時のスタック不足で停止した。逆アセンブルでsetupのフレームが0x1b10（6928）バイト、FatFsのFILが大きな内部バッファを含むことを確認した。試験側のLogWriterをヒープへ移してsetupを0x170（368）バイトへ縮小した。通常実装のLogWriterはApplication内のStorageTaskが静的に所有しており、この試験側の配置は使用しない。

修正後の実機保存テストは成功した。64件保存後の65件目の拒否、保存後の同一セッション再開、65件のCRC読戻し、同一秒の別ファイル1件、同一session_idの拒否、空セッションの非作成、試験ファイルとディレクトリの削除を確認した。出力は`[STORAGE-TEST] PASS records=65+1 CRC=OK overflow=OK pause/resume=OK collision=OK empty=OK cleanup=OK heap=330444 stack_free=5096`。これはStorage単体の試験イメージであり、通常アプリの空きヒープとは区別する。

G0を押して起動した後はUSBのダウンロード状態を保持する場合がある。試験時はesptoolのESP32-S3定義にある強制ダウンロードフラグを解除し、watchdog_reset後のUSB再接続へ追従してログを取得した。通常ファームを書込み・ハッシュ照合後に起動し、DISPLAY、4T/5Q、NVS LOADED、FAT32、GPS UART、DATASET OPENの6項目が正常となり、BootからLive Placeへ進むことを確認した。実GPSのFix・JST時計・習志野市の地名検索、64KiBキャッシュのMISS後のHITを確認し、30秒の取得中に例外や再起動を検出しなかった。実機のキーを用いた開始から停止までの一連操作は、この検証では自動実行していない。UIモデルと実機の保存処理はそれぞれ上記の試験で確認した。

通常アプリのキャッシュ確保後の空きヒープは145,932〜146,332バイト（約143KiB）、最小空き138,140バイト、最大連続129,012バイトだった。Storageの最小残スタック観測値は7,380バイト。ビルド時の静的RAM使用は43,448 / 327,680バイト、Flashは1,050,001 / 3,342,336バイト。

通常ファームSHA-256: `3035f9c5ec464538ed10e9034ca104ae9823a594e09890377ed3af246ab9fdeb`。試験イメージは残しておらず、更新した通常ファームで稼働する。
