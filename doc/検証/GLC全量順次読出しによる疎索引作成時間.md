# GLC全量順次読出しによる疎索引作成時間

計測日: 2026-10-20。製品ソースの基準は`baf271e`。GLCをシークせずに全量読み、Nバイト間隔のブロック位置索引をRAM上へ作成する方式を実機で測定した。Nは直前の検討に合わせて65536バイト（64KiB）、読出しバッファは4096バイトとする。

## 対象と索引の配置規則

Cardputer ADV、MAC `70:af:09:df:46:d0`、CPU 240MHz、SD SPI 4MHz。対象は`/sd/dataset/02/estat-r2ka-jgd2011-2020-grid-8192-10000.remap.wgsmapset.glc`、23,800,183バイト、162個のGI01とする。[前回の全ブロック列挙](全チャンクのブロック位置列挙時間.md)と同じデータセットである。

対象は格納サイズがNより大きい78チャンク。チャンク先頭の位置には既存のGI01索引を使う。各GI01先頭を基準とするN、2N…の境界について、境界以上にある最初のブロック先頭を追加索引に採用する。同じ先頭が複数の境界に対応する場合は重複登録しない。境界の後にブロック先頭が存在しない場合は追加しない。

追加索引は32bitの絶対ファイル位置と32bitのブロック番号の組でRAMへ実際に格納した。チャンク別に、追加索引配列の開始要素と件数を保持する。画像の展開と索引のSD保存は行わない。比較・検証のため、対象外を含む全23,679ブロックの位置と長さも列挙・検証し、従来と同じ64bitハッシュを計算する。

## 順次読出しの実装

診断用Readerはファイル先頭で一度だけ開く。通常ならスキップする本文も同じ先読みバッファへfreadし、RAM内の位置を進めて読み流す。fseekは初期位置指定も含めて使わない。

WGSMapSetのメタデータとGI01群は同じストリームで処理する。形式判定のために先読みした最初の`GI01`の4文字はRAMから再提示し、ファイルを開き直したり先頭へ戻ったりしない。チャンク境界でもバッファを引き継ぐ。このため、ファイル全体の取得量が厳密に23,800,183バイト、Open/Closeが各1回、fseekが0回であることを試験の完了条件にした。

計測はSDマウント・NVS復元の後、通常のデータセット検証より前に一度実行した。Factory・ファイルの準備、メタデータ解析、既存GI01索引の作成、疎索引のRAM確保・登録、全ブロックの位置・末尾検証と位置ハッシュを含む。SDマウント、Wordbook、画像展開、索引のファイル保存、結果ログ出力、作成済み疎索引の検査用ハッシュ計算は含まない。進捗ログの呼出し時間だけは別計測して差し引く。GPSとUIタスクは継続し、ReaderのSD/RG表示通知は無効とする。

## 実機結果

| 項目 | 実測値 |
|---|---:|
| 索引作成時間（進捗ログを除く） | 72.544882秒 |
| 実経過時間 | 72.550565秒 |
| 進捗ログ時間 | 5,683 µs |
| fread時間 | 72.346033秒 |
| fread取得量 | 23,800,183 B（ファイル全体と一致） |
| fread回数 | 5,811回 |
| fseek回数・時間 | 0回・0秒 |
| Open / Close | 各1回 |
| 索引対象チャンク | 78個 |
| 作成・保持した追加索引 | 303件 |
| 追加索引本体 | 2,424 B |
| チャンク別参照表 | 1,296 B |
| 追加索引配列の実確保容量 | 2,904 B |
| 位置・長さの64bitハッシュ | `344960485833343087` |
| 疎索引の検査用64bitハッシュ | `495159520715346536` |

配列の実確保は363件分で2904バイト、チャンク別参照表は1296バイトで、合計4200バイト。C++コンテナ等の管理情報と既存のGI01索引はこの値に含まない。不要本文も含めて全量を読み、デコーダへ渡した78,908バイトとRAM内で読み流した23,721,275バイトの和がファイルサイズと一致した。

固定バイト区切りで算出した304件に対し、実際のブロック先頭を使うと303件になった。差はチャンク72で生じる。格納サイズ526,338バイトに対し、最後の64KiB境界は524,288バイト、最終ブロックの先頭は514,463バイトで、それ以降に新しいブロック先頭がないため追加しない。この位置関係はPython SDKでも確認した。

## 前回との比較

同じデータセット・実機・4KiBバッファによる各1回の測定を比較する。

| 方式 | 所要時間 | fread取得量 | fread回数 | fseek回数 |
|---|---:|---:|---:|---:|
| 前回：既存Readerで全ブロック位置列挙 | 139.375981秒 | 17,599,060 B | 4,297 | 4,272 |
| 今回：全量順次読出し＋疎索引RAM保持 | 72.544882秒 | 23,800,183 B | 5,811 | 0 |

今回の時間短縮は47.95%だった。前回は全ブロック位置を列挙・検証するが全索引を保持せず、今回は疎索引を保持する。今回の方式ではメタデータと本文のReaderも統合しており、スキップ関数だけを変更した比較ではない。

Nを変更しても全ファイルを読む方式であるため、読出し量は変わらない。変化するのは索引の件数・保持量・登録処理である。別のN・読出しバッファ・SDに対する実機時間はこの測定では取得していない。時間は他タスク実行・媒体待ちを含む経過時間であり、SPIバス単独の時間ではない。

## 検証と生成物

ホストでは4・8・16KiBのバッファで同じ全量順次読出しを実行し、全件の位置・長さハッシュ、疎索引303件の位置とブロック番号、ファイルサイズ・末尾、シーク0回、各1回のOpen/Closeの一致を確認した。実機でも同じハッシュになった。全量を一度読むことと、前回の位置列挙結果を維持することを同時に検証した。疎索引303件のCSVは`.pio/sequential-index-bench/sparse-index.csv`に保存した。ホストの時間を実機値としては扱わない。

診断コードは`.pio/sequential-index-bench/application`と`include`の一時コピーであり、製品ソース・SDK・設定は変更していない。差分は`diagnostic-source.patch`、生ログは`device.log`、集計は`results.json`、事前検証は`host-results.log`とする。

診断ファームは`.pio/sequential-index-bench/benchmark-firmware.bin`、1,138,144バイト、SHA-256 `59089312a25770cf8ee21a52f89d420a3bed12a1d772ee348736c43589a8977a`。ビルドは警告・エラーなく成功し、静的RAMは77,728バイト、Flashは1,137,781バイトだった。MACと書込みハッシュの照合に成功した。試験後は保存済みの通常4KiBファーム（SHA-256 `1f8b633f8c3a8039340156a08dabfee5d5f40d9be03b1f8b8c2c0cfe07653df8`）へ戻し、書込みハッシュ照合に成功した。NVS・SDの消去は行っていない。復帰後30秒のログでLoRa SLEEP、FAT32、GPS測位、Galuchat OPEN OK、Boot Ready、習志野市の地名表示とキャッシュヒットを確認した。通常検索の地図読出しは716800バイト・175回・シーク174回で、診断の索引作成は実行されていない。復帰ログは`.pio/sequential-index-bench/restore-boot.log`。診断用のELFと中間生成物は同ディレクトリの`diagnostic-build`へ退避し、標準の`.pio/build/cardputer-adv/firmware.bin`も通常版へ戻した。診断ELFを通常ファームのシンボルとして使わないよう分離している。
