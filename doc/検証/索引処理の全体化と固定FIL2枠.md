# 索引処理の全体化と固定FIL2枠

2026-10-28。データセット適用時の部分再利用を廃止し、索引の生成・元データ突合を全体処理へ統一した。バイナリ形式version 1と既存索引の読出し互換は維持する。

## 適用・再生成・検証

| 操作 | 処理 |
| --- | --- |
| 適用・既存索引が正常 | 構造・CRC、GLCの識別情報、必要な全言語と各Wordbookの対応を確認し、索引を書き換えず選択を保存する |
| 適用・索引が欠落／不足／不一致／破損 | 地図と全言語Wordbookを一時ファイルへ全再生成し、構造・CRCと元データから再計算した全索引レコードを検証してから公開する |
| キャッシュ再生成 | 既存内容を部分コピーせず、常に全再生成・全体検証する |
| キャッシュ検証 | 全索引レコードを元GLC・全言語Wordbookから再計算し、既存ファイルへ書き込まず照合する |

正常な既存索引の採用は、元データ本文の全走査突合とは区別する。同じファイル名・サイズ・FAT更新日時・ヘッダを保持した本文変更まで検出する処理ではない。全文からの索引レコード再計算は明示検証で行う。

部分再利用の`ReusePlan`・コピー処理と、Map / WordBooks / Reuseの対象指定を削除した。UIの対象番号選択と確認の経路は維持し、内部APIも全体単位に揃えた。生成と比較は同じ`generate`を使い、出力先だけを書込み／照合へ切り替える。

索引公開前に、同期・閉鎖と生成前後の元ファイル識別情報の一致を確認する。生成・検証・公開・設定保存の失敗は成功扱いにせず、旧正式索引と選択を維持・復元する。復元にも失敗した場合は区別したエラーと退避ファイルを残す。既存の一時・退避ファイルを自動採用しない。正常な索引をそのまま採用するときは不要な一時ファイルを操作しない。

## 固定FILの所有と借用

`StorageWorkArea`が`ReadFileSlots`を固定メンバーとして2枠所有する。LogReader / MapBuildJobを入れるvariantの外へ置くことで、画面・ジョブ切替後もFILのアドレスと所有者は変わらない。StorageTaskのメンバー順も、貸出し元がPlaceLookupのFactoryより長く生存する順へ揃えた。

| 利用者 | 使用枠・同時数 |
| --- | --- |
| 地図生成 | 第1枠を事前確認・索引・GLCで順に使用、最大1個 |
| ログ閲覧 | 第1枠。統計計算中など必要な期間だけ保持 |
| 地名検索 | 第2枠を索引・GLC・Wordbookで順に使用、最大1個 |
| 候補GLC調査 | 座標ReaderとGI01 Readerで最大2個 |
| 既存索引の適用可否確認 | 索引Readerと各Wordbookの確認Readerで最大2個 |
| 索引生成 | 一時ファイルと元データReaderで最大2個 |
| 索引突合 | 比較対象索引と元データReaderで最大2個 |

索引のSourceと出力は同じ短寿命の`IndexFile`ラッパーを使用する。出力ラッパーのヒープ確保もなくした。FILを借りたまま3枠目が必要になれば、追加の動的FILへ逃げず失敗する。終了・例外時は貸出しを返却する。ログ閲覧ではFatFsのclose失敗時にFILを保持して再試行する既存方針を維持する。一時出力の同期・閉鎖失敗後は公開せず、一時ファイルを破棄する経路へ戻す。

通常記録のLogWriterとUSBエクスポートは独立した所有者のまま。VFS内部の管理領域も本表の2枠とは別。索引適用・保守はログ停止・保持セッションなしの既存条件を維持する。先読み4KiBや出力バッファなど、FIL以外の作業域の確保方式は今回変更しない。

## メモリ

ESP32-S3のビルド／ELFから確認した値。この表はSD専用版へ移行する前のSDK標準版の値で、FILは1個4,136 B。その後の移行結果は[固定FIL2枠とSD専用FatFsの実機比較](固定FIL2枠とSD専用FatFsの実機比較.md)を参照。

| 項目 | 変更前 | 変更後 | 差 |
| --- | ---: | ---: | ---: |
| 共通FILの枠数 | 1 | 2 | +1 |
| `ReadFileSlots` | — | 8,280 B | FIL 8,272 B＋貸出し管理・padding 8 B |
| `StorageWorkArea` | 4,816 B | 8,968 B | +4,152 B |
| 通常ファーム静的RAM | 259,672 B | 263,832 B | +4,160 B |

`MapBuildJob`はFILを内包せず136 B、`LogReader`は672 Bとなる。通常ファームの静的RAM使用率は80.5%。増加分と引換えに、索引生成・検証のネイティブFILの都度確保をなくし、3個同時に開く部分再利用経路を除去した。動作中のヒープ残量・処理時間の新しい実機測定は本作業に含めない。

## 検証

- 索引テスト：実N03と合成データで構造・CRCを独立パーサと照合。既存索引の無書換え採用、不足言語による全再生成、CRC不正時の全再生成、全体突合、書込み・同期・閉鎖・公開・NVS保存・復元失敗を確認。処理中の最大貸出し数2と全返却も確認。
- 作業領域テスト：2枠の同時貸出し、3枠目の拒否、ジョブ切替前後のアドレス保持、close失敗・取消・古い結果、100回の無割当切替を確認。
- Readerテスト：stdioとFatFs互換アダプタ、診断ON/OFFで借用領域・I/O一致・例外回収・close失敗後の保持と再試行を確認。
- 地名検索：N03とestatでログ閲覧相当の第1枠を保持し、第2枠のみを使う7点の検索を実施。地名・区域コード・キャッシュ結果が従来結果と一致し、正常・読込失敗後に第2枠を返却することを確認。
- 地図生成：N03の1/1・1/2・1/4で区域コード画像・境界画像の一致、Reader／借用領域の回収と地図生成経路のC++割当0を確認。
- Native / Appテスト：UI・設定・GPS・ログ閲覧・履歴地図・リプレイ・USBの既存テストを通過。
- ESP32-S3通常ファームのビルドを実施。その後SDK版とSD専用版を実機比較した。計測と最終ファームの情報は上記の比較記録へ分離した。

本環境はptrace下でLeakSanitizerが動作しないため、Native系のASan実行は`ASAN_OPTIONS=detect_leaks=0`を指定した。ASan / UBSanと、貸出し状態・ハンドル数・確保回数による検査は維持している。
