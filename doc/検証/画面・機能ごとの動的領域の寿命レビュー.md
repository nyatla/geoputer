# 画面・機能ごとの動的領域の寿命レビュー

調査日: 2026-10-26

## 判定基準と結論

最新の3件のメモリ整理を含む実装を対象に、確保元・所有者・解放条件を静的に追跡した。今回はレビューのみで、アプリと実機ファームは変更していない。追加の動作試験・実機測定は行っていない。

寿命が画面→機能→一時I/Oに収まることと、実際のmalloc/freeが厳密な逆順になることを分けて評価する。所有者が親子でも、関数内で作った結果の配列を呼出し元へ移す場合や、vectorの再確保・画像のswapでは、確保順序の入れ子は成立しない。現在は画面ごとの一括確保領域で全ヒープを管理する構成ではない。

画面専用の大きな領域はおおむね整理されている。UI地図画像は画面切替とログの地図→文字で解放し、Storageの区域画像もCloseMapSessionで解放する。一方、小さな作業文字列の保持、消灯中の画像、共通キャッシュ、処理結果の寿命の持上げには以下の例外がある。いずれも直ちにメモリリークを意味しない。

## 画面・機能の境界に収まらない領域

| 項目 | 現状の寿命 | 判定と整理案 |
|---|---|---|
| LogReaderのpath_ | 一覧・概要等の処理後もReaderに容量を残す。cancelも容量を解放しない。完了済みでログ画面からLIVE／設定へ移る場合、Storageへ終了の通知がなく、次のforMap等でReaderを破棄するまで残る。通常の/sd/logsでは56文字＋終端の予約 | ログ画面群単位でも個別要求単位でも閉じていない。意図した再利用だが、画面群終了と未完了要求の終了を合わせて解放する境界が不足。USBのファイル選択→変換／再公開でも同じ容量が残る |
| LogWriterのpath_ | 記録終了後のflushでFILを閉じてもパスが残る。次のopenのclearも容量は解放しない | 記録セッションより長い。容量再利用の設計。全保存・close成功後に解放する案はあるが、保存失敗・close失敗・再試行中は維持が必要。UI画面単位に合わせる対象ではない |
| 消灯中のUI地図画像 | View→Backgroundは画面を変更せず、copyDataも表示モードではclearしない。Storageの区域画像はprocessMapで閉じるが、UIのfront/backは残る。最大6,060 B×2 | 地図画面には収まるが、表示中の機能単位では閉じていない。復帰直後に旧画像を表示する方針との交換条件。未表示のbackだけを解放する案と、両方を解放する案を区別する |
| UI地図のfront/back | commitでswapし、更新が完了しても旧frontを次のbackとして保持する | 画面単位では整理済み。1回の更新単位には収まらず、厳密な確保逆順もswap回数次第で成立しない。画面単位の2枚プールとして扱うのが実態に合う。更新ごとに解放すると確保頻度が増える |
| StorageのMapSession区域画像 | UIの画面切替後もCancelMap／CloseMapSessionの受付完了まで残る。例示条件で79,680 B、設定上限96KiB | 厳密なUI画面終了時刻を跨ぐが、未完了I/O・転送の終了処理として必要。Appは要求識別子と世代を画面用unionの外に保持して繰返し閉じる。早期解放の対象ではない |
| 128×128の区域コードキャッシュ、地名検索Factory、表示書式 | PlaceLookupにあり、画面変更では解放しない。64KiBの画像は一度確保するとデータセット変更・再マウント等のcloseまで保持 | 画面単位には収まらないが、複数画面が使うデータセット共通資源として意図されている。LIVE・地図・ログごとに複製していない。画面別へ移すなら再読出し・再確保の増加を評価する |

根拠:

- LogReader.hのpath_、LogReader.cppのpathFor／cancel／releaseForReuse、StorageWorkArea.hのforMap／forLogs。
- Application.cppのsetScreen、LogBrowser.cppのprepareLogScreen、StorageTask.cppのCancelLogRead受付。完了済み要求はCancelLogReadの対象にならない。
- LogWriter.cppのopen／requestFlush／flush。
- UiModel.cppのsetScreen／copyData／updateContent、MapFrameReceiver.hのcommit／clear。
- MapView.cppのprocessMap、StorageTask.cppのCancelMap／CloseMapSession受付、StorageScreenResources.hの2つのMapSession。
- PlaceLookup.cppのconfigure／releaseReaders／close、CachedMapReader.cppのrebuild。

## 機能内でも確保順序が交差する箇所

| 箇所 | 交差する順序 | 評価 |
|---|---|---|
| 地図の初回生成・容量拡張 | MapSourceのメタデータ・パス・Factoryを確保→MapSessionの区域配列を確保→一時Factory等を解放→区域配列を画面表示中保持 | 結果を親セッションへ持ち上げる構造。所有権は明確だが厳密なLIFOではない。同容量を再利用する更新では区域配列の確保がなくなる。必要なら親の確保を一時Readerより前へ寄せる準備順序を検討するが、再読出しや余分な常駐量を増やさないことが条件 |
| WordbookのTI00／TT00／TM00 | ページ用Readerを確保→SDKが結果vector/stringを確保→Readerを破棄→結果を検索終了まで保持、または上位のresultへ移動 | 検索全体のスコープには収まるが、個別ページ読出しの中へは閉じない。codes・token_sets・fragmentsや戻り値が該当。最近のids共用は重複を減らしたもので、検索全体を一つのarenaにしたものではない |
| メタデータと索引生成の戻り値 | ファイル／Sourceが生存中にDatasetMetadataやBookSource配列を構築し、ファイル等を閉じた後にも結果を返して利用する | 設定の各操作には収まる。戻り値の寿命の持上げによる非LIFO。全てを一時Readerの領域へ置くことはできない |
| vector/stringの容量拡張 | 新領域を確保→内容を移す→旧領域を解放→新領域を継続使用 | 関数スコープが正しくても逆順解放にはならない。可変長の結果・ネストしたvector等に残る。必要件数のreserveや借用領域で減らす対象 |
| ObservedFileReaderの構築失敗 | 自己所有バッファを確保→FILを確保→f_open失敗でthrowすると、buffer_がfile_より後の宣言なのでbuffer_から先に巻き戻る | 正常終了はcloseFileがFILを先にresetするため逆順。失敗時も両方は解放され、リークではない。失敗時まで逆順に揃えるならメンバー宣言順を整理する候補。借用バッファには4KiBのヒープ解放自体がない |

MapSource.cpp、DiskIndexedWordBookReader.cpp、DatasetMetadata.cpp、DatasetIndex.cppのbookSources、ObservedFileReader.hを確認した。SDKのreadCodeSetFromRoot／readTokenIdSetsFromPage／readTokensFromPageは値として結果を返す契約であり、変更時はSDKとの互換性を別途検討する必要がある。

## 整理済み・共通資源として維持する部分

- Appの画面用データは固定のAppScreenResources、UIのページ情報は固定のUiData内にあり、画面変更でヒープを確保する構造ではない。ログの10件キャッシュも固定配列。
- UIの主フレーム16,204 Bと文字描画の20 B領域は既に所有者内の固定領域。メニュー・GPS・ライセンス本文・ダイアログ用の大きな動的画面データは見つからなかった。
- 地図のUI画像は別画面への移動とVによる文字表示でclearする。通常地図とログ地図のStorage Sessionは別インスタンスで、他方を解放して使う。
- 地図生成の4KiB索引バッファは固定境界画像を借用し、返却後に同じ配列へ境界画像を生成する。生成の途中と画像転送中の用途切替を拒否する。
- 索引生成のSource／OutputのFile・バッファは各操作の終了までに破棄する。複数入力・旧索引・出力が同時に存在するため、同じ領域へ無条件に重ねることはできない。
- USBのExporterは変換時に確保し、close成功後に破棄する。close失敗時の保持は、エラー画面の見た目より長くても未完了の後処理として必要。約11KiBのオブジェクトをそのままStorageのスタックへ置く案は除外する。
- キーボードReader、キー状態vector、UIのパレット、FreeRTOSのタスク資源は画面共通のタスク／ドライバ寿命。画面ごとに作り直す対象ではない。GPSアプリ側のNMEA行・フィールド配列も既に固定領域。

## スタック化できそうな残り

| 候補 | 方法・効果 | 難度 |
|---|---|---|
| アプリ側の16 B固定シグネチャ照合 | DatasetIndex.cppのWGSMapSet/3・GisWordBook/0の照合をchar[16]とstring_viewへ。現在のreadBStrAsciiは最初に16文字のstringを作るため、末尾NULを除去しても一時的なヒープ確保がある。必ず16 Bを消費し、最初のNUL以降の扱いを従来どおりにすれば、SDKを変更せずアプリの呼出し箇所だけで対応できる | 低 |
| LogWriter::createFileのファイル名組立て | 日時またはundatedの接頭辞、連番、.gps.datを既存LogNameBytes内のchar配列へ整形し、持続するpath_へ直接追記する。ディレクトリは可変長のまま維持する。連結中間文字列を減らせる。既にprefix[64]とtime[24]がスタックにあるため、それらも含めて配置を整理する | 低 |
| MapSource内の一時Factory本体 | 同期関数内だけで使う2個のFactory本体（各56 B）をローカルへ置き、アプリ側DiskIndexedMapReaderが参照を借用する形。ただし現APIはshared_ptrを所有するため、単純置換は不可。永続PlaceLookup用の所有関係は維持する。path文字列まで全てスタックになるわけではない | 中・API整理が条件 |

4文字のtag用string、短いja/en、to_string(uint32_t)などはSSOに収まるため、char配列へ変えても通常はヒープ削減にならない。既に実施した言語ID配列・行バッファ・描画用配列は新しい候補へ重複計上しない。

Reader本体76 Bは小さいが、ReaderFactoryがunique_ptrを返す契約のままではスタックに置けない。FIL約4,136 B、4〜16KiBのI/Oバッファ、可変長Wordbookの全配列、64KiBキャッシュ、区域画像、USB Exporterは今回の小さなスタック化候補から除外する。固定化のために新しいデータ上限は設けない。

## 優先順位

画面境界の整理はLogReaderのパス領域が最も追いやすい。次に、LogWriterの正常終了後のパス保持と、消灯中のUI画像の方針を整理する。非LIFOな結果返却を全て作り直す作業は大きいため、ページ用の作業領域と画面が保持する結果領域を分けて設計する段階で扱う。

小さなスタック化は16 Bヘッダ照合とログのファイル名組立てを先に検討できる。Factory／Readerの借用API変更は別作業とし、スタック上のオブジェクトを通常のunique_ptr／shared_ptrへ渡して寿命を偽装しない。

`a5f431df02b3dc5c023835be72f48d00250eacf9af438f6ca1b6784128ae1d61`
