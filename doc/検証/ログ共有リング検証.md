# ログ共有リングの検証

検証日: 2026年10月16日

## 1. 実装と通信

ログ追加のAppendLog同期メッセージを廃止し、App上で実行する`StorageTask::tryAppendLog`へ変更した。[LogWriter](../../application/task/storage/log/LogWriter.cpp)の排他付き64件リングへ直接格納し、受付成否を関数の戻り値、LogSnapshotを値コピーで返す。AppはGPS通知の処理中に追加するため、別の同期要求の結果待ち中もStorageのSD処理終了を待たない。開始・flush・終了の制御は従来の同期メッセージ、実保存結果はLogWritten / StorageError通知とする。

保存済み・受付済み件数はLogSnapshot自身のrevisionで照合し、古いStorage通知で直接受付後の状態を上書きしない。セッション切替でも同revisionを維持する。受付満杯・容量エラーは従来どおり画面のエラー状態へ渡す。

## 2. 容量・排他・保存

レコード配列は32バイト×64件、連番配列は32bit×64件で計2,304バイト。旧Entry配列と同じ容量であり、保存用の追加レコード配列や二重バッファを持たない。未保存の64件には保存中の領域も含める。Appに従来からある受付失敗時の1点保持は維持する。

Storageは保存対象を短い排他区間で固定し、ロックを外してSDを操作する。折返しは最大2連続区間を直接writeし、f_sync成功後に対象件数だけ解放する。失敗時は対象・保存位置を固定し、後から追加された点を保ったまま再試行する。保存中に追加された最初の点の受付時刻も保持し、その後の保存期限へ使用する。

32バイトの符号化用ローカル領域と、従来の512バイトヘッダー領域は使用する。ESP32向け生成コードの関数入口で確認したスタックフレームはappendが96バイト、flushが592バイト、snapshotが48バイト。これは各関数自身のフレームであり、呼出し先を含む最大スタック使用量ではない。全件をスタック上で連続化する領域は存在しない。

## 3. ホスト検証

`python3 tests/run_native.py`は-Wall / -Wextra / -Werror、UndefinedBehaviorSanitizer、pthread付きで成功した。[共有リングの試験](../../tests/log_ring_tests.cpp)で次を確認した。

- 40件を保存対象として固定したままSD処理を待機させ、別スレッドから24件を追加できた。65件目は満杯を返し、成功後に元の40件だけを解放した。
- 折返す50件（24件＋26件）の保存中に10件を追加し、OSのファイルサイズ制限で先頭区間より後の書込みを失敗させた。保存件数を進めず全60件を保持した。
- 失敗後に残り4枠へ追加し、終了要求を出した。再試行では元の50件だけを保存し、後続14件と終了要求を維持した。次の保存で終了した。
- 合計104件を全バイト比較し、順序・内容・CRC・件数と、保存失敗後の重複がないことを確認した。
- 追加側と保存側を別スレッドとして2,048件を連続処理し、繰返すリングの折返しでも全点の順序・内容・CRCとカウンターの整合が一致した。
- 古い状態による件数の巻戻りを拒否し、セッション切替後の新しいrevisionを受け付けた。

既存の部分書込み復旧、64件上限、命名・CRC、設定・GPS・UI・ライセンス等の試験も成功した。ThreadSanitizerはホスト環境に`libtsan_preinit.o`がないためリンクできず、同サニタイザーでの検証は実施していない。

## 4. ファームウェアのビルド

`PLATFORMIO_CORE_DIR=/tmp/geoputer-pio-core /tmp/geoputer-pio-venv/bin/pio run -e cardputer-adv -j 4`は成功し、コンパイラの警告・エラーはなかった。静的RAMは45,640 / 327,680バイト、Flashは1,060,281 / 3,342,336バイト。静的RAMは変更前の45,456バイトから184バイト増加した。レコード保持容量は維持し、増分は排他・リング管理・状態世代等のためのものである。

生成物は`.pio/build/cardputer-adv/firmware.bin`。SHA-256は`74726be71531eed6286ac8b9f166ce7bed0ab5427814363cdf96dc5784363e1f`。

## 5. 実機の専用保存試験

2026年10月16日、COM6のESP32-S3（MAC `70:af:09:df:46:d0`）を照合し、[専用試験ファーム](../../tests/hardware/storage_log/README.md)をアプリ領域0x10000へ書き込んだ。SHA-256は`3234f5aeed7299759e1281aa1a59e97a1ac7576970410d1a98e6d4c2ad809a6f`。書込み後のハッシュ照合は成功した。FAT32のSDを既存の4MHz接続でマウントし、NVS・既存ログ・データセットを変更せず、ランダムID付きの試験専用ディレクトリを使用した。

追加側をCPUコア1、保存側をCPUコア0で動かし、保存対象を固定した直後のSDアクセス区間を試験用セマフォで待機させた。その間の41〜64点、91〜104点の追加はいずれも成功し、各試行で65件目相当の新規受付を満杯として拒否した。追加処理の最大所要時間は両試行とも24µs。前者の保存後はsaved=40・buffered=24、後者はsaved=90・buffered=14となり、後続点を解放せず残した。

最後に104件をSDから読み、時刻順・座標・各CRC・EOFを確認した。従来の65件＋1件の保存・CRC、pause/resume、同秒名の衝突回避、空セッションも成功した。`[RING-TEST] PASS`と`[STORAGE-TEST] PASS`、`cleanup=OK`を確認し、今回作成したファイル・ディレクトリだけを削除した。試験終了時の空きヒープは330,312バイト、setupの残スタックは4,008バイト。ログは`.pio/ring-hardware-test.log`へ保存した。

この24µsは人工的に保存側を待機させた試験での測定値であり、実媒体I/Oと追加処理の時間的な重なり、通常ファームの最大受付遅延・空きヒープを示す値ではない。実機での部分書込み失敗・媒体障害は意図的に発生させておらず、その復旧は3節のホスト試験で確認した。

## 6. 通常ファームの書込みと起動

専用試験後、4節のSHA-256と一致する通常ファームウェアを0x10000へ戻し、書込み後のハッシュ照合を確認した。再起動ログで240×135のUI、4タスク・5キュー、NVS設定読込み、FAT32、GPS UART、Galuchatデータ、LivePlaceへの遷移を確認した。GPSの有効FixとJST補正、習志野市の地名取得、矩形・WordBookの初回MISSからHITへの遷移も正常だった。起動後のStorage残スタックは7,404バイト、空きヒープは143,932バイト、最小ヒープは135,940バイトを報告した。ログは`.pio/ring-normal-boot.log`へ保存した。

ユーザーの実キー操作による記録開始後に監視を再開し、通常ファームで約180秒の保存継続を確認した。観測した保存件数は28件から178件へ単調に増加し、16回のLogWritten相当のログはいずれもerror=0だった。保存結果のbufferedは0または1で、保存対象外として残った後続点を次回以降へ保存していた。最後のGPS診断はFIX・rejected=0・coalesced=0で、panic・assert・再起動を示すログはなかった。ログは`.pio/ring-recording-trial.log`へ保存した。

延長した監視でも保存件数793件までerror=0を確認した。延長監視は15:13:41に10分の時間上限で終了し、その後にユーザーから停止操作実施の申告を受けたため、停止イベント自体は取得できていない。16:06台にリセットせず再接続し、40秒間に有効Fixを39件受信したが、新たな保存・ログ制御イベントは出力されなかった。再接続区間は`.pio/ring-after-stop.log`へ抽出した。これは書込みが継続していないことを支持するが、一時停止とファイル終了を区別する証拠にはしない。

停止操作後、ユーザーがGPS Logger画面でSAVED=3527、UNSAVED=0、BUF=0/64、LOST=0を確認した。通常ファームで3,527件を保存し、Appの受付待ちを含む未保存点・リング残件・計数された欠落がいずれも0であることを表示値から確認した。記録継続中の保存成功、停止操作後に追加書込みがなくGPS受信を継続すること、および停止後のバッファ消化までを今回の実GPS試験の結果とする。

記録開始・停止の制御ログは監視時間外のため取得していない。画面上段のSTOP / CLOSINGは未回答であり、物理クローズ完了をログ・状態から直接確認したとは扱わない。一時停止・再開の操作と実GPS記録ファイルのCRC読戻しも未確認であり、開始→一時停止→再開→停止の全通し試験完了とは扱わない。

## 7. 検証範囲

専用試験以外での通常運転の最大受付時間・残スタック・長時間の記録は未確認である。ログ一覧・詳細・測位点閲覧も未実装のため、記録中の実閲覧試験を完了したとは扱わない。GPS通知キューの容量・統合規則は変更せず、満杯が続く場合の無欠落を保証するものではない。
