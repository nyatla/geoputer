# 3件の小規模メモリ整理の実機比較

実施日: 2026-10-26

## 結果

Wordbookの番号配列の段階間共用、短い言語IDのスタック化、LogReaderのパス領域再利用を実装した。確保・解放の頻度は減ったが、今回の前後各2回の実機比較では全体のピーク使用量の改善は確認できなかった。起動後最低空き量の最悪値は47,548→47,348 Bで200 B減った。平均値も47,568→47,452 Bだった。小さな領域の削減を、そのまま実機全体の削減量とは扱わない。

地図読出し8回の合計時間は平均1,779.5→1,771.5 ms（約−0.45%）で同程度だった。静的RAMは85,504 Bのまま、Flashは1,225,933→1,226,001 B（+68 B）。通常ファームを書込み済みで、SD・GPS FIX・データセット・地名表示を確認した。

## 実装と寿命

- DiskIndexedWordBookReaderのsortedとtokensを1本のidsへ統合した。TT00の対象選択を終えてから内容を消し、TM00の対象番号を収録する。必要なトークン数を先に数えてreserveし、再利用元の容量を倍増した結果、不要に大きな容量を確保することを防ぐ。表示順のcodesと、同時に必要なtargets・token_sets・fragmentsは維持する。検索を終えると作業配列も解放し、検索間の容量保持は行わない。
- dataset.iniの現在セクション名は32 Bのスタック配列で保持し、string_viewで参照する。索引検証では前の言語IDを32 B配列へコピーし、現在のIDはレコード内のstring_viewで比較する。最大31文字、NUL終端、重複・降順の拒否を維持し、返却する言語一覧・ファイル名・表示文字列は所有するstringへコピーする。短いja等は従来もSSO内に収まるため、元々ヒープ確保がない。
- LogReaderはpath_を所有し、最初の使用時にdirectoryの長さ＋LogNameBytes分の容量を予約する。一覧のstat・記録中ファイルの判定・概要・測位点・削除で同じ文字列を組み立て直す。容量はReaderが有効な間保持し、MapBuildJobへの切替などでReaderを破棄すると解放する。ファイルごとの確保は減るが、処理の合間にもパス容量を保持する。パス長の固定上限や新しいファイル名規則は導入しない。

Galuchat本体・Core・SDK、I/O順序、ファイル形式、キューと操作手順は変更していない。Reader共用の4KiB削減は変更前から有効であり、今回の差へ重複して数えない。検索間の作業配列保持や索引生成I/Oのセッション化は未実施である。

## 対象上のサイズとスタック

対象ESP32-S3ツールチェーンで、LogReaderは4,688→4,712 B（+24 B）。MapBuildJobは6,176 B、StorageWorkAreaは6,192 B、StorageScreenResourcesは6,464 Bで変わらない。LogReaderの増分は既存variantの最大領域に収まる。

| 関数 | 変更前 | 変更後 |

## ホストでの確保回数と生存量

同じ計測プログラムを変更前後それぞれへリンクし、N03・estatで比較した。以下はC++の要求確保回数と、計測区間内で新たに確保された領域のピーク生存バイトであり、FatFsやstdio内部のC確保、allocatorの管理情報、実機全体の使用量ではない。結果のfingerprintとWordbookのbytes／read／seek／open／close回数は全ケースで一致した。

| ケース | C++確保回数・前→後 | ピーク生存量・前→後 |
|---|---:|---:|
| N03・Wordbook検索24回 | 1,067→982 | 5,316→5,276 |
| estat・Wordbook検索24回 | 1,327→1,230 | 10,625→10,561 |
| 短いIDだけのメタデータ解析20回 | 80→80 | 293→293 |
| 31文字IDを含むメタデータ解析20回 | 200→180 | 293→293 |
| 31文字IDを含む索引検証20回 | 100→40 | 4,192→4,128 |
| 32ファイルのログ一覧・初回 | 64→1 | 308→151 |
| 同じログ一覧の再走査20回 | 1,280→0 | 308→0 |
| 同じReaderでログ概要取得20回 | 40→0 | 308→0 |

Wordbook検索24回の要求確保バイト累計は、N03が180,620→177,772 B、estatが415,760→411,880 B。この累計を同時に空くメモリとは扱わない。

メタデータの長いIDのケースは31文字のIDを2つとjaを宣言し、解析と索引の並び順を検証した。ログ一覧は長いホスト用ディレクトリの32ファイルを対象とする。変更後の初回パス確保151 Bは、そのReaderの存続中は保持する。通常の/sd/logsでは予約容量は56文字＋終端となり、実際の確保サイズはallocatorに依存する。ホストのC++確保ゼロという値を、実機のfopen等を含む全確保ゼロとは解釈しない。

## 実機比較

Cardputer ADV（MAC 70:af:09:df:46:d0）、FAT32、選択済み01・162チャンク。SPI指定25MHz、実クロック20MHz。前後各2回の独立した起動で、同じ自動操作を実行した。固定の習志野付近の座標を基準に、通常地図・区域変更・範囲外移動・帰還・1/2・1/4・ログ地図・文字表示・退出、その後に既存ログの一覧・概要・測位点0／10／20を読む。4回とも全地図読出しがerror=0で完了した。

ログの記録・削除、索引再生成、NVS設定保存は行わない。比較版だけに2048 Bの採取タスクを追加し、1ms間隔・Reader構築時・段階切替時に採取した。表は各区間のサンプル最小値であり、空き量と最大連続空き領域の最小値は同時刻とは限らない。min_bootはallocator自身の起動後最低値である。通常ファームの絶対的な最低空き量とは区別する。

各セルは1回目／2回目、単位B。

最大連続空き領域も、全段階のサンプル最悪値で33,780→32,756 Bとなり、改善は確認できなかった。今回の2試行ずつでは変動要因を分離できておらず、長時間の断片化改善を主張する結果ではない。

## 検証と保存

- run_native.py：メタデータの31／32文字境界・行バッファ再利用・UTF-8、ログ一覧・読出し・削除、UI・GPS・USB・設定などの回帰試験。
- run_storage_work.py：180文字のディレクトリ要素と32ファイルで、初回パス確保1回、再走査と概要読出しで追加のC++確保なしを確認。共用領域・取消・close失敗の既存試験も成功。
- run_dataset_index.py：実データ・人工データで従来Readerとの地名一致、索引形式・CRC・部分再生成・失敗時復旧、31文字の共通接頭辞を持つ言語IDの比較、CRCが正しい重複／降順／終端なしIDの拒否を確認。容量予約を加えた最終版でも成功。
- run_memory_three_host.py：N03／estatの計測と、結果fingerprint・Wordbook I/Oの完全一致。ASan／UBSanを使用し、実行環境の制約によりLeakSanitizerは無効。
- 通常版と比較版のPlatformIOビルド、ESP32-S3の型サイズ・フレーム比較、対象差分の空白検査。
