# GPS・Application通信検証

対象設計: タスク構成設計 Draft 0.7（旧同期方式）  
適用範囲: 結果取得タイムアウトで要求を終了する旧方式。現行の[タスク構成設計](../06_タスク構成設計.md)の検証結果には適用しない  
検証日: 2026-10-14  
検証方法: Python標準ライブラリによる離散イベントシミュレーション  

## 1. 結論

通常通知と同期戻り値のキューを分ける構成は、測位・UI・保存状態の通知を戻り値と誤認せずに処理できる。同期要求の要求ID照合とタイムアウトにより、モデル内で別の要求を成功扱いにしたり、Appが無期限に待機したりする動作は発生しなかった。

ただし、Appの同期呼出しが同時1件でも、タイムアウトした旧要求がGPS側で処理中のまま残る。旧要求と新要求の戻り値が競合すると、容量1のAppReturnQueueから新要求の正しい戻り値が失われる。待機開始前のキュー掃除と受信時の要求ID照合だけでは防げない。

また、長い同期待ちで通常通知とGPSの一時保持容量を超えると、測位サンプルが欠落する。現状取得の繰り返しは実状態の確認を可能にするが、変更に失敗した設定を反映する動作にはならない。

構成の骨格は成立するが、無条件に破綻しない設計とは評価できない。期限切れ戻り値の扱い、許容同期待ち時間と通知保持容量、状態不一致後の制御条件を確定する必要がある。

## 2. モデルと適用範囲

Appが持つApplicationQueueと容量1のAppReturnQueue、GPSのGPSQueueをモデル化した。AppからGPSへ同期要求し、GPSからAppへ通常通知・戻り値を投機的送信する。Appは同期待ち中に通常通知を処理せず、呼出し終了後に処理する。

GPSは要求を順次実行する。同じ時刻にGPSとAppが実行可能ならGPSを先に実行する。即時の現状取得は同じスケジュール区間で完了するものとした。この実行順序は設計のGPS優先方針と両立するが、実機の時間測定結果ではない。

キュー操作はモデル内で不可分とし、GPSは通知送信でブロックしない。GNSS UARTの物理受信、休止プロトコル、タスクのコア割当、割り込み、メモリ使用量、SD処理は再現していない。業務処理の失敗・通知未達・実行時間は試験入力として指定する。

通常通知の容量8、GPS要求の容量4、GPSの未送信サンプル保持2を基本の仮定値とした。容量超過試験では通常通知容量を4に変更した。これらは製品の確定値ではない。UI・Storage通知は通常通知への混入確認用に入力し、両タスク自体はモデル化していない。

## 3. 検証結果

| 試験 | 結果 |
|---|---|
| 初期化 → ACTIVE → 測位通知 | 同期結果を受信し、測位サンプルを通常通知として処理した |
| 同期待ち中の測位・UI・Storage通知 | 3通知を通常キューに保持し、同期終了後にすべて処理した |
| 設定成功・戻り値未達 → 現状取得 | ACTIVEを確認できた。設定変更は1回だけ実行した |
| 設定失敗・戻り値未達 → 現状取得を10回 | すべてPAUSEを返した。変更要求を再実行しないため目標ACTIVEには移行しなかった |
| 旧要求の遅延戻り値と次の要求 | 旧戻り値が容量1を占有し、次の正しい戻り値が投入できずタイムアウトした |
| 要求期限を超えた戻り値をGPS側で抑止する比較モデル | 同じ競合例で次の現状取得が成功した。現行設計への採用はしていない |
| 1 Hz通知・9秒の同期待ち・通常キュー4＋一時保持2 | 9サンプル中6件を保持・処理し、3件が欠落した |
| GPS要求キュー満杯 | QueueTimeoutとなり、その要求をGPSは実行しなかった |
| 別要求ID・別種別の戻り値 | 現在の要求の戻り値として採用せず、正しい結果を待てた |

遅延応答の実行時間、現状取得の処理時間、Appの実行遅延を変えた156通りも確認した。48通りで戻り値の投入競合が発生したが、全156通りで後続の現状取得は成功した。この数は入力条件の組合せ数であり、実機での障害発生確率や任意の実行順序での回復保証を示さない。

## 4. 戻り値キュー競合の時系列

| 時刻 | 動作 |
|---:|---|
| 0 ms | Appが初期化要求ID=1を送る。期限は100 ms |
| 100 ms | ID=1の同期待ちがタイムアウトする。GPS側の初期化は継続中 |
| 101 ms | Appが現状取得ID=2を送る。期限は201 ms。待機開始時点で戻り値キューは空 |
| 120 ms | GPSがID=1を完了し、旧戻り値をAppReturnQueueへ投入する |
| 同じ区間 | GPSがID=2を処理する。キューは旧戻り値で満杯のため、正しい戻り値の投機的送信に失敗する |
| その後 | Appが旧戻り値を取り出し、ID不一致として除外する。ID=2の結果は届かない |
| 201 ms | ID=2がタイムアウトする |
| 250 ms | 次の現状取得ID=3は成功する |

要求ID照合は誤認を防ぐが、キュー投入失敗を防ぐものではない。タイムアウトはApp側の待機終了であり、旧要求のGPS側処理終了ではない。

## 5. 設計で確定する条件

1. 期限切れの旧戻り値が、次の同期要求の戻り値キューを占有することを許すか。許す場合は不要なタイムアウトを含めて復旧する契約が必要となる。
2. Appの最大同期待ち時間と通常通知の保持容量。初期占有数、通知頻度、ほかの通知の流入、GPS一時保持容量を含めて見積もる。
3. GPSの目標状態と確認した実状態が不一致の場合の制御。現状取得の再試行と変更要求の再実行は別の動作とする。

比較モデルでは同期要求に期限を持たせ、GPSが結果を送る時点で期限を過ぎていればその戻り値を送らない。この規則で今回の競合例は解消した。ただし、期限確認と投入の間のプリエンプション、期限内に送られた結果の滞留などは別に検証する必要がある。比較結果だけを根拠に実装上の競合がすべて解消したとは判断しない。また、戻り値の抑止は実行済みの設定変更を取り消さない。

## 6. 再現方法

リポジトリのルートで次を実行する。Python標準ライブラリ以外の依存はない。

```sh
python doc/検証/gps_app_simulation.py
```

[シミュレーションコード](gps_app_simulation.py)は現行設計の8ケースと比較モデル1ケース、156通りの実行順序を検証する。[結果と全時系列](gps_app_simulation_results.json)は実行時に再生成する。現行タスク構成設計の通信規則は、この検証によって変更していない。
