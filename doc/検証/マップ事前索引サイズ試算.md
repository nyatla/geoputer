# マップ事前索引のサイズ試算

2026-10-21、提案した逐次読出し用レイアウトを実データへ当てはめた。GLCの全ブロックの開始位置と格納長をCoreのPython Readerで列挙し、群数から索引ファイルの論理サイズを算出した。索引生成の本番実装、SD上の索引作成、ファームの変更は行っていない。Wordbook用の索引は含まない。

## 集計規則

- ヘッダー64バイト、全チャンクについて40バイトのチャンク情報、群ごとに16バイト、末尾CRC32が4バイト。
- GI01識別子・可変長サイズ欄・本体を含むチャンク全体が16KiB以上の場合に群を作る。16KiB未満は群数0。
- 最初のブロックから格納バイト数を加算し、64KiB以上になったブロックの末尾で群を確定する。次の群は次のブロック先頭から開始する。
- 最後の未確定分があれば、64KiB未満でも1群として記録する。ブロック途中では分割しない。
- 群はブロック0から最後まで隙間なく覆う。元マップのチャンク・ブロックの順序を維持する。

```text
索引サイズ = 64 + チャンク数 × 40 + 群総数 × 16 + 4
```

## 統計区高精細版の内訳

| 項目 | バイト数 |
|---|---:|
| ヘッダー | 64 |
| チャンク情報：162 × 40 | 6,480 |
| 群情報：404 × 16 | 6,464 |
| 末尾CRC32 | 4 |
| 合計 | 13,012 |

元GLC 23,800,183バイトに対し約0.055%。16KiB未満の53チャンクは群を持たず、残る109チャンクに404群を作る。1チャンクの最大群数は18、最大群サイズは77,329バイト。ブロック境界で確定するため、群サイズに64KiBの厳密な上限はない。

4KiBの索引読出しバッファなら、索引全体は4回の補充に相当する。これはバイト数からの計算であり、SDでの実測時間や物理セクタ読出し回数ではない。ファイルシステム上の割当容量も別になる。

## 検証と保存物

全データでチャンク末尾、群の連続性、対象チャンクの全ブロックを群が覆うこと、閾値による群数0の条件を検査した。統計区高精細版の全23,679ブロックの位置・長さハッシュは `344960485833343087` となり、以前の実機・C++列挙結果と一致した。

以前の303件は固定64KiB境界に対応する追加の疎索引であり、今回の404件とは定義が異なる。今回は16KiB以上を対象にし、各対象チャンクの先頭群も含めて数えている。群ごとに64KiBへ達した時点で確定する規則も適用した。

`.pio/map-index-size-estimate/`に集計スクリプト `count.py`、概要のJSONL、チャンク・群ごとの位置・件数・長さと元ファイルのSHA-256を含むJSONを保存した。
