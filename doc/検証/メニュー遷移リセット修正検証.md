# メニュー遷移時のリセット修正検証

更新日: 2026-10-17  
対象: Live Placeで「2」を押したときのAppスタック不足

## 1. 原因

実機で「2」を押すと、`Stack canary watchpoint triggered (loopTask)`を伴うパニックと再起動を再現した。バックトレースは、readUiContent → setScreen → callUi → sendSync → xQueueGenericSendを示していた。

データセットの詳細表示を追加したUI要求は1,544バイトになっていた。UI操作取得用の要求と結果を保持したまま画面切替へ進み、画面切替要求の集約代入の一時オブジェクトと、sendSyncの値渡しによる要求全体のコピーも重なり、ArduinoのloopTaskの8KiBスタックを超えていた。UIタスクのキーバインドや、データセットの再起動要求が原因ではない。

パニックと修正前のログは`.pio/menu-reset-panic.txt`、`.pio/menu-reset-before.log`に保持する。修正前のELFは`.pio/menu-reset-before.elf`に保持する。

## 2. 修正

sendSyncは呼出し元の変更可能な要求を参照で受け、ヘッダーだけをその領域へ設定する。受信タスクへ渡す値コピーは既存FreeRTOSキューへの投入時に行う。画面切替・内容更新は要求ペイロードの各フィールドへ直接代入し、UiDataを含む集約初期化の一時コピーを作らない。

GetUiContentの要求と同期結果はreadUiSnapshot内に閉じ、小さなUiSnapshotだけをreadUiContentへ返す。取得が終わってから操作を処理するため、操作取得と画面切替の大きな要求領域が同時に存在しない。readUiSnapshotはnoinlineを指定し、最適化時もスタックの寿命を分離する。

タスク数、キュー数、キューの値コピー契約、通知・戻り値の待機方式、スタック容量、キャッシュ容量は変更していない。UI要求のための新しい常駐バッファも追加していない。画面遷移のログへloopTaskの最小空きスタック量を追加した。

## 3. ホスト試験とビルド

`python3 tests/run_native.py`が成功した。追加試験では、呼出し元の要求へのヘッダー設定、結果待機中の重複送信拒否、投入後の要求領域再利用とキュー内の独立した値コピー、元の要求IDによる戻り値照合を確認した。既存のUI遷移、同期タイムアウト・遅延応答、GPS、設定、ログの試験も成功した。

PlatformIOのcardputer-advビルドが成功した。リンク済みELFの逆アセンブルから、各関数のentry命令によるスタック確保量を確認した。

| 関数 | 修正前 | 修正後 |
|---|---:|---:|
| callUi | 1,584 B | 32 B |
| setScreen | 3,440 B | 1,936 B |
| publishUiContent | 3,440 B | 1,936 B |
| readUiContent | 1,920 B | 128 B |
| readUiSnapshot（新設、取得後に復帰） | — | 1,920 B |

不具合の経路に重なっていたreadUiContent・setScreen・callUiの確保量の合計は6,944 Bから2,096 Bへ4,848 B減った。この合計は該当3関数だけの値であり、RTOS・キュー操作・割込み等を含む総使用量ではない。

静的RAMは53,376 Bで変更なし。Flashは1,070,917 Bで、直前のUTF-8専用版から132 B減った。

ファームウェアSHA-256: `0236fac78f8cacc1816a2cd319313fe8ce27dda8691467f8b8722023c9895e56`

バイナリは`.pio/menu-stack-firmware.bin`、ビルドとホスト試験のログは`.pio/menu-stack-build.log`と`.pio/menu-stack-native.log`、比較結果は`.pio/menu-stack-results.json`に保持する。

## 4. 実機起動

COM6のCardputer ADV（MAC `70:af:09:df:46:d0`）へアプリ領域のみを書き込み、esptoolの照合成功を確認した。NVS・SDの内容は変更していない。

再起動後はSDのFAT32マウント、データセット01のOPEN OK（172チャンク）、GPS FIX、習志野市の地名表示まで確認した。以前のINI・ファイル名の不一致は解消している。起動時のloopTask最小空きスタックは4,408 B、Live Placeへ自動遷移した時点で4,108 Bだった。

起動ログは`.pio/menu-stack-boot.log`、書込みログは`.pio/menu-stack-flash.log`に保持する。


## 5. データセット切替後のUI監視タイマー

メニュー・設定画面への遷移が成功した後、ユーザーが「適用して再起動」で別のデータセットへ切り替えた。切替先は162チャンクのGLCで、NVS復元・ヘッダー確認・Live Placeへの遷移に成功した。その後、`task_wdt: IDLE0 (CPU 0)`による別の再起動を捕捉した。バックトレースはUIの文字描画中を示しており、前述のloopTaskスタック不足とは別の事象だった。

UIループは10msの絶対周期をvTaskDelayUntilで維持していた。描画・連続更新で周期を超過すると、遅れを取り戻す反復が休止なしで実行され、CPU 0のIDLEを実行できなくなる。各反復の最後をvTaskDelayの相対10ms待機へ変更し、描画に時間を要しても毎回ブロックしてIDLEへ実行機会を渡す。キーリピート・時計は実時間に基づくため、その判定方式は変更しない。監視タイマーは無効化・延長しない。

この事象のログとELFは`.pio/menu-ui-watchdog-before.log`と`.pio/menu-stack-before-yield.elf`に保持する。前節までのSHA-256と容量はスタック修正単体の値であり、UI待機修正を含む最終版の値とは区別する。


## 6. 最終版の実機検証

スタック削減とUIの相対待機の両方を含む最終版をビルドし、同じ端末へ書き込んだ。esptoolの書込み後照合は成功した。静的RAMは53,376 B、Flashは1,070,893 B。スタック確保量は3節の修正後の値と一致している。

最終版SHA-256: `a36bc283ad6338b66eea3d122f656d199e6d08aaffb108f2078d6a6418ee0a3e`

再起動から90秒間、USBシリアルを連続取得した。切替済みの162チャンクのデータを読み込み、約8.25秒の初回地名検索と、その後のキャッシュヒットに成功した。ユーザーの実キー操作によるLive Place → MENU → SETTINGS → Live Place、さらにMENUを開いて戻る操作を記録した。GPS受信は継続し、スタック保護例外・監視タイマー停止・意図しない再起動は記録されなかった。画面遷移ログのloopTask最小空きスタックは2,440 Bだった。この値は今回の実機操作中の測定値であり、すべての操作経路の最大使用量を保証するものではない。

バイナリは`.pio/menu-fix-firmware.bin`、書込みログは`.pio/menu-fix-flash.log`、90秒の起動・操作ログは`.pio/menu-fix-boot-operations.log`、検証結果は`.pio/menu-fix-results.json`に保持する。ホストの同期通信・UI契約試験も成功しており、`.pio/menu-fix-native.log`に保持する。
