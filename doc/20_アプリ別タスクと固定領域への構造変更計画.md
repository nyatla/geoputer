# アプリ別タスク・固定領域への構造変更計画

2026-10-30。状態：実装済み（ホスト試験・実機向けビルドを検収、実機書込み・Wi-Fi通常起動を確認、他モードの実機操作は未確認）。基準コミット`e3afb88`から、以下の構造変更を実装した。現行配置は[メモリ構成設計](18_動作モード別メモリ構成設計.md)、数値は[検証記録](検証/アプリ別タスクと固定領域の検証.md)を参照する。

## 1. 目的と完了条件

GPSロガー、USBストレージ、Wi-Fi管理を、それぞれ専用のApp処理・UIタスク・Storageタスクと固定資源を持つ独立したアプリケーションとして構成する。最上位のunionは起動するアプリ全体を重ね、各アプリの型にはそのアプリが使うタスクと資源だけを置く。

同じタスククラスに全モードの状態を持たせ、モードフラグで処理を切り替える構成を解消する。タスクの実行基盤・描画・ファイルI/O等の部品は共用し、状態の所有者とタスク実装はアプリごとに分ける。

完了条件は次のとおりとする。

1. 選択アプリ以外の固定資源を、選択アプリの型に含めない。USB・Wi-FiのUIには地図の表示・受信画像を持たせない。
2. 各タスクは自分の固定状態と作業領域を所有する。並行動作するタスクの領域を重ねない。
3. 最上位の固定予約を増やさない。各アプリの型サイズ・最上位union・外側の管理領域を、実機向けELFで比較する。
4. GPS記録、地名検索、地図、ログ閲覧、アラート、USB転送・エクスポート、Wi-Fi管理の外部動作を維持する。
5. アプリ変更は保存して再起動とし、タスク稼働中のunionの再構築を行わない。

## 2. 固定メモリの比較基準

現行のApplicationModeMemoryはApp・Storageの一部のモード専用資源を重ねた部分unionであり、共通UI・フレームバッファ・キュー・App/UIの表示状態・Storage共通管理はその外側にある。

今回の最上位unionには、これらを含むアプリ全体を収める。そのため、現行の部分union単体と新しい最上位union単体のsizeofを比較して、増減を評価してはならない。元の外側領域を残しながら内側へ同じ領域を追加することも禁止する。

直前のビルド済みESP32-S3 ELFで確認した基準は次のとおり。

| 基準 | 容量 |
| --- | ---: |
| 静的Application全体（モード領域・UI・キュー等を含む） | 219,528 B |
| ファームウェアの固定データ領域（.dram0.data＋.dram0.bss） | 281,908 B |
| Flash | 1,803,781 B |

基準バイナリSHA-256：`424679af25f82098cc918b74f1e543d6d521d7c60a74ed3fee2bd6db90dc203f`。ソースは現行コミットに対応し、このバイナリはコミット前に生成されたため、埋込みGit情報は新規ビルド時に更新される。

新しいApplicationRuntimeの固定予約は、最上位unionと外側の選択タグ・ディスパッチ管理を合算して219,528 B以下を目標・検収条件とする。タグ・参照・vtable・アラインメントの増加を無視せず、増加が生じた場合はその原因を整理してから採否を判断する。最終的な固定RAM全体も281,908 B以下を確認する。

USB・Wi-Fiが小さくなっても、物理的な最上位予約は最大のGPSアプリに合わせて残る。排除するのは各アプリの型の中に埋め込まれた他モード専用領域である。この違いを計測表で明示する。RTOSスタック、SDKのグローバル領域、ライブラリ内部ヒープは別枠であり、この変更だけで全システムをヒープレス化したとは扱わない。

## 3. 目標構造

```text
ApplicationRuntime（起動アプリの選択とmainからの呼出し）
├ 選択タグ・最小限のディスパッチ管理
└ ApplicationMemory : union
  ├ GpsApplication
  │ ├ GpsApp処理・App通知／結果キュー・同期管理
  │ ├ GpsUiTask・専用モデル・表示領域・画面内作業union
  │ ├ GpsStorageTask・記録／検索／地図／索引領域・作業union
  │ └ GpsTask・受信状態・受信キュー
  ├ UsbApplication
  │ ├ UsbApp処理・App通知／結果キュー・同期管理
  │ ├ UsbUiTask・USB画面モデル・表示領域
  │ └ UsbStorageTask・媒体制御・一覧／変換処理と作業union
  └ WifiApplication
    ├ WifiApp処理・App通知／結果キュー・同期管理
    ├ WifiUiTask・接続／QR画面モデル・表示領域
    └ WifiStorageTask・HTTP／DNS・固定FIL・転送領域
```

App処理は引き続きArduinoのloopTask上で動かし、App用のRTOSタスクを追加しない。初期移行ではGPSの4タスク、USB・Wi-Fiの3タスクという構成を維持する。ただし共通のタスク構成や共通の具象クラスを前提にせず、各アプリが自分のタスクを構築・起動する。

起動アプリの全タスクオブジェクトは、一つのアプリメンバーの中へ直接構築する。全モード用の具象UiTaskやStorageTaskをunionの外へ置かない。アプリ間で大きな共通状態を継承する基底クラスは作らず、共通化は小さな部品やテンプレートで行う。

### 3.1 タスク内のunion

同時に生存する固定状態はタスクの通常メンバーに置き、機能・画面内で排他になる作業だけを内側のunionへ置く。

- GPS UI：常用の画面描画バッファ、地図の表示・受信用画像、借用中の管理状態は共存可能な別領域として維持する。画面ローカルの排他状態は内側で重ねる。
- GPS Storage：区域コードキャッシュ64 KiBと地図区域コード画像96 KiBの独立性を維持する。96 KiBの地図／索引作業の排他利用と、Reader／FIL借用を引き継ぐ。
- USB Storage：USB媒体・コールバック・排他状態は常用部として保持する。ファイル一覧読出しとエクスポートの作業を内側で整理する。GPS用MapBuildJobを含む現在のStorageWorkAreaをそのまま流用しない。
- Wi-Fi Storage：HTTP/DNSの制御、操作中の固定FILと転送4 KiB、進捗・保存先を持つ。今後の排他的な処理追加も、この所有領域内で設計する。

並行動作するUIとStorageのタスク領域自体は重ねない。GPS UIのオフスクリーンと、Storageへ貸出中の受信画像も重ねない。完了後まで保持する表示画像や結果は、生成ジョブだけの作業領域と寿命を分ける。

## 4. アプリごとの責務

| アプリ | App | UI | Storage |
| --- | --- | --- | --- |
| GPS | 起動確認・GPS・記録・画面遷移・地名／地図借用・履歴・アラート | GPS用の各画面、地図2枚、表示用データ、設定、音声 | SD・設定、記録、ログ読出し、データセット、地図・地名、索引、アラートファイル |
| USB | 媒体公開・ローカル操作への切替、エクスポート、終了 | USB状態、一覧・形式選択・進捗・確認 | 生セクタ公開との排他、一覧、エクスポート、同期・再公開 |
| Wi-Fi | 接続状態の表示反映、認証情報再生成、終了 | 接続QR・URL QR・文字情報、状態、確認 | HTTP/DNS、ファイル操作、保存・回復、状態通知 |

USB・Wi-Fiの型にはGPS状態、地名・地図画像、GPSログ記録バッファ、区域アラート、GPS用の画面状態を含めない。Wi-Fi Appが現在のAppUsbResourcesを流用する構成も解消し、Wi-Fi固有の必要量だけを保持する。

同じ描画形式を使う画面バッファは各アプリのUIに一つずつ記述するが、実際の予約は最上位unionで重なる。ROM上のフォント、アイコン、Webコンテンツ等は共用する。

## 5. 共通化する部品と通信

共用するのはTask／Queue／同期通信の基盤、メッセージの小さいヘッダー、表示・キー入力・描画部品、ハードウェア制御、SD専用FatFs、ログ形式・変換・Galuchatアダプター等の機能部品とする。共通タスクのモード分岐へ処理を戻さない。

UiData、UiRequest、StorageSnapshot、通知・応答のpayloadはモード別の型へ整理する。USB・Wi-Fiのキューが、GPSの地図・データセット・アラート情報を含む最大メッセージを予約する構成を解消する。列挙値・小さい共通ヘッダーまで無理に複製しない。

Appは通知キューと数量1の同期結果キュー、サブタスクは受信キュー一つという通信原則を維持する。同期要求のタイムアウト後も結果を受け取るまで待機状態を保持する規則を変えない。サブタスクからの通常通知は投機的送信とし、必要な状態保持・再通知を維持する。

GPSのUI→App→Storageのメモリ借用は、GpsApplication内で完結する型付き参照として維持する。画面を切り替えても処理終了前に貸出領域を再利用しない。Appからログ記録を共有RAMリングへ渡す既存経路と、その排他も維持する。

## 6. 起動・切替・余白の寿命

起動部はLoRaの安全停止、起動モード読出し、選択アプリの構築、USB初期化に必要な呼出し順を管理する。大きなアプリオブジェクトを一時スタックへ作らず、最上位unionへ直接構築する。

USB MSCのインターフェース登録はUSB開始より前に行う。SD周辺機器の初期化は表示・基板初期化との既存の順序を守る。各アプリは必要なタスクとキューだけを開始する。

Wi-Fiの未使用末尾のヒープ登録は、選択したWifiApplication全体の末尾から計算する方式へ移す。従来の部分unionのアドレス・サイズを使い続けない。生存する全タスク・バッファ・選択タグ等を除外し、静的領域内であることと整列を確認し、登録は起動中一度だけとする。登録後に同じ領域へ他アプリを再構築しない。

USBの余白を新たなヒープやアプリ専用アリーナとして使う機能は、この構造変更と区別して検討する。最上位unionを小さいモードごとに縮小する機構は導入しない。

アプリ切替は従来どおり起動フラグの保存と再起動を使う。USBコールバックやFreeRTOSタスクが生きている間に、その所有アプリを破棄しない。初期化失敗時にも他モードを同じメモリへ即座に構築し直さず、選択アプリのエラー処理または再起動で扱う。アプリ全体の破棄は起動管理が一度だけ行い、Storageタスクが最上位unionを破棄する現行の所有経路を廃止する。ホスト試験で破棄する場合はタスク・コールバック・借用の停止を先に確認する。

## 7. 作業順序

1. **基準と配置検査を固定する。** 現行コミットの型サイズ、固定RAM、Flash、キュー容量・スタック予約、代表動作を記録する。新旧の外側領域を二重予約していないことを確認できる検査を用意する。
2. **起動選択と最上位unionを導入する。** 現在のApplication全体を暫定的な旧アプリとして最上位へ収め、mainからの呼出しを小さい起動管理へ移す。旧大領域を別のグローバルとして残さない。この段階でも最大固定予約を増やさない。
3. **Wi-Fiアプリを独立させる。** WifiApplication／WifiUiTask／WifiStorageTaskと専用のUI・通知型を実装し、QR・Web・ファイル操作・再生成・終了を移す。地図・ログ・音声の状態を持たせず、末尾のヒープ登録を新配置へ対応させる。
4. **USBアプリを独立させる。** UsbApplication／UsbUiTask／UsbStorageTask、USB用モデル・通信・作業領域を用意する。媒体公開・ローカルFS・一覧・エクスポート・再公開を移し、GPS用のStorageWorkAreaや画面状態への依存を除く。
5. **GPSアプリを独立させる。** 残る起動・記録・GPS・UI・Storage・借用をGpsApplicationの所有へ移す。GPS UIの地図画像と音声もこの内側へ置く。既存の処理順序・キュー方式を保ちながら、USB・Wi-Fiの型や分岐を外す。
6. **暫定構造を除去する。** 共通具象Application／UiTask／StorageTask、モードフラグによる通常処理の分岐、旧部分unionへのアクセス、不要な互換アクセサーを削除する。共通部品とモード専用状態の境界を確認する。
7. **型とメモリを検収する。** アプリ・各タスク・各内部unionのサイズ表を出し、最上位unionと外側を合算して基準内であることを確認する。別モード専用メンバーが混入していないこと、固定画像・FIL・キューの所有者とアドレスが安定することを検査する。
8. **動作確認と仕様更新を完了する。** モードごとのホスト試験、実データ、ブラウザー、ビルドを確認して現行構成仕様を更新する。実機確認では各モードの起動・復帰・既存機能とメモリを測定する。

移行途中の旧アプリと新アプリはソース上で共存してよいが、固定メモリは同じ最上位unionへ重ね、稼働させるアプリを一つにする。動作確認のために旧・新の大きな領域を並べて保持しない。

## 8. 検証項目と変更範囲

| 対象 | 確認内容 |
| --- | --- |
| 構築・寿命 | アプリ一つだけを構築。他アプリ・不要なGPSタスクを開始しない。別モードの領域へアクセスしない |
| メモリ配置 | GPS／USB／Wi-Fi、各タスク、内部union、外側管理の32 bitサイズ。UIの地図2枚がGPSだけに存在。USB／Wi-Fiのメッセージ容量にGPS情報が混入しない |
| GPS | 起動・メンテナンス、測位・時刻・地名、記録開始／一時停止／停止、ログ閲覧・地図・再生、設定・データセット・索引、区域判定と音声 |
| 借用・排他 | 地図・地名・索引の貸出、画面変更・取消・遅延完了、ログ書込み／読込みの既存排他、Reader／FIL返却 |
| USB | PCからの読書き、ローカルFSとの排他、エクスポート、取消・失敗・再公開・終了 |
| Wi-Fi | QR・認証情報、日英3画面、単体ファイル操作と編集、同名置換・回復・削除、認証再生成・終了、余白登録後の起動とメモリ |
| 予算 | ApplicationRuntimeの固定予約は219,528 B以下、固定RAM全体は281,908 B以下。スタック予約・SDKヒープを別に報告 |

SD上のファイル形式、NVSの起動フラグ・設定形式、HTTP API、表示・キー操作の外部仕様は維持する。Galuchat本体・SDKの変更、USBエクスポーターの固定化、WebServerや無線SDK内部のヒープ排除、タスクスタックの静的化はこの構造変更とは別の作業として扱う。
