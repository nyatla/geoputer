# 地図生成の残存ヒープ調査

調査日: 2026-10-28。本資料はFactory・内部Readerのスタック化直後の調査記録である。その後、[選択中データセット情報の統合](選択中データセット情報の統合.md)により、地図生成ごとのINI読込み・解析とパスの組立て・コピーを除去した。以下の残存確保一覧は統合前の状態を示す。対象は通常版のStorage地図生成経路である。索引の生成・検証、起動処理、地名検索単独の経路まで無確保を保証するものではない。

## 1. FactoryとSDK内部Readerの保持方式

`readBoundaryMap`の索引用・GLC用`ObservedFileReaderFactory`は局所変数として構築する。`DiskIndexedMapReader`は既存の参照コンストラクタで両Factoryを借り、Factoryより先に破棄する。要求終了後に参照を残さない。Factoryの`make_shared`と管理ブロックの確保を取り除き、汎用SDK互換のshared_ptr経路は維持する。

SDK内部の`GaluchatImageDataChunk01Reader`は、`LimitedReader`をunique_ptrから値メンバーに変更した。通常チャンクと外部索引のブロック群の両方で、デコーダと同じ寿命で保持する。自己メンバーを指すポインタは置かず、ムーブ後も元の入力と位置・ビット状態を引き継ぐ。コピー禁止、ムーブ構築・代入可能な性質、入力の消費順序と末尾検証は維持する。

ESP32向けの型サイズはFactoryが1個60 B、LimitedReaderが24 B、GI01デコーダが変更前32 Bから48 Bとなる。2個のFactoryはスタック上に置き、デコーダ内部では従来のポインタ類を24 Bの値に置き換える。これらは型のサイズであり、関数のスタックフレーム全体や高水位の測定値ではない。大きな読出しバッファやFILをスタックへ移したわけではない。

変更はReverseGeoputer内のGaluchatヘッダに限定し、Core・SDKには同期していない。

## 2. 残る動的確保と寿命

| 対象 | 確保の発生箇所 | 寿命・重複 |
|---|---|---|
| パス文字列 | `directory + "/_mapindex.dat"`、`directory + "/" + metadata.map`、Factoryの所有パスへのコピー | 地図生成要求内。元のパスとFactory側のコピーが同時に生存する |
| FatFsパス変換 | `fatFsPath`が返す`std::string` | stat・openの各呼出し内だけ生存する |
| INI解析結果 | map・wordbook・title・description・言語・表示書式の文字列、言語ID配列 | メタデータ取得後もGLC読出し完了まで生存する |
| INIの標準IO | `fopen`のFILE管理領域と読出しバッファ | ストリームはメタデータ解析完了時に閉じる。読出しバッファは閉じる際に解放。FILE管理領域はnewlibが再利用する |

短い文字列は標準ライブラリ内部に収まる場合があるため、文字列操作の全てが必ずヒープ確保するとは限らない。通常の長いGLCファイル名では所有パスとコピーが削減候補になる。

### INI解析

地図の再生成ごとに`readDatasetMetadata`を実行する。1回のopenの中で先頭へ戻して2回走査し、1回目に共通項目・各言語セクションの整合性を確認して言語IDを集め、2回目に対象言語の値を取得する。各行は既存の256 Bスタック配列とstring_viewで解析しており、行ごとの切出し文字列を追加生成する実装ではない。

地図生成が利用するのは主にmapファイル名と解析の成否だが、現在は地名用のWordbook名・表示書式や設定表示用のタイトル・説明も取得する。FILEは解析関数から戻る前に閉じる一方、結果オブジェクトの文字列・言語配列は地図生成の最後まで生存する。

### 標準IOとVFSの区別

実環境はESP-IDF 4.4.7／newlib 3.3.0である。INIのみ標準IOを使い、GLC・保存索引の本体読出しはFatFs直結の`ReadFile`を使う。

ESP-IDFのFAT VFSは、登録時に`max_files`個のFILを含むコンテキストを一括確保し、open時はその空きスロットを利用する。現設定は3スロット、FILは4,136 Bなので、FIL配列分は12,408 Bとなる。コンテキスト・FATFS・フラグなどは別に必要である。これはSDマウントからアンマウントまで保持する初期化時の領域であり、INIを開くたびに4,136 Bを追加確保するという意味ではない。地図生成用のStorage固定FILとは別の領域である。

newlibのFILEスロットは空きがなければ管理領域を確保し、閉じた後は再利用する。ストリームの読出しバッファは別に確保される。今回のXtensa用ヘッダでは`__BUFSIZ__`が128に定義され、実際にリンクされる`__swhatbuf_r`の逆アセンブルでも既定値128 Bを確認した。FAT VFSのfstatはst_blksizeを0にするため、INIの通常読出しではこの128 Bが選ばれる。標準のstdio.hにある汎用の1,024 Bという値をそのまま当てはめない。ヒープ管理情報やFILE管理領域を含む総量を128 Bとみなしてはならない。

参照: [ESP-IDF 4.4.7のFAT VFS](https://github.com/espressif/esp-idf/blob/v4.4.7/components/fatfs/vfs/vfs_fat.c)。newlibのサイズ・確保経路は、このビルドで使用したtoolchainのsys/config.h、libc.aのfindfp・makebufとリンク済みELFで確認した。

## 3. 次の改善候補

1. Factoryが要求内の所有パスを参照する方式にし、Factoryへのパスコピーをなくす。Factoryと利用側Readerが要求の外へ出ない条件を維持する。
2. 長さを検証する固定長パス組立てとFatFs変換を導入する。現状はstd::stringが長さを管理するため、上限と超過時のエラーを先に定義する。
3. 地図生成用に必要項目だけを保持するメタデータ取得経路を作る。全セクションの検証方針を維持しつつ、タイトル等の保持を省く。解析結果を常駐キャッシュする場合は、USB編集・SD再マウント・データセット切替時の無効化が別途必要になる。
4. INI読出しを固定FILと借用バッファによるFatFs経路へ移す。INI解析完了後に索引・GLCを読むので寿命は排他になる。単にsetvbufで読出しバッファを渡す方法だけでは、FILE管理領域の確保は残る。VFS全体のスロット削減は起動等の同時open要件も確認して別途判断する。

これらは調査結果であり、今回の変更には含めない。

## 4. 検証

- `tests/run_galuchat_ranges.py`: 既存の逐次Readerトレース、矩形・範囲・ブロック群・RAW/RLEと異常系を確認した。追加したchunk_storage_testで、通常チャンク・範囲復号のC++動的確保0、元デコーダ破棄後のムーブ構築・代入を確認した。
- `tests/run_borrowed_map_files.py`: estatの習志野付近で1/1・1/2・1/4の区域コード画像と境界画像が一致し、事前確認失敗時の借用返却も確認した。
- 同ホスト条件のC++ new要求サイズ累計は、借用経路で直前の886／886／926 Bから566／566／566 Bとなった。これは要求ごとの累計であり、実機のピークヒープ使用量ではない。stdio内部のmalloc、ヒープ管理情報は含まない。一時ディレクトリ等のパス長でも変わる。
- 通常構成`cardputer-adv`のビルド成功。静的RAMは259,384 Bで直前から変化なし。Flashは1,239,841→1,239,269 B（572 B減）。実機書込み・実機時間計測・スタック高水位の再測定は実施していない。
