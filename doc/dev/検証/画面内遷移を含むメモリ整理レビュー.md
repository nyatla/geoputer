# 画面内遷移を含むメモリ整理レビュー

調査日: 2026-10-26

後続作業として、本書の1・2・3を実装した。[実装と比較結果](返送領域・索引検証・UI画像のメモリ削減.md)を参照。以下は改修前のレビュー記録である。

本書は改修候補の評価であり、採用済みの実装仕様ではない。アプリのソースと実機ファームウェアは変更していない。画面群だけでなく、画面内の表示モード、Storageの処理段階、起動時の動作モードまで寿命を分解して調べた。

動的確保から静的確保への変更だけでは総RAM削減にならない。常駐量、処理中の最大使用量、確保回数を区別する。他の用途の固定領域と重ねられる場合に、静的確保と実質的な削減を両立できる。

## サイズの確認

ESP32-S3用の現行ツールチェーンとArduino SDKヘッダーでsizeofをコンパイルし、オブジェクトのシンボルサイズを調べた。ホストPCのポインタサイズによる推計ではない。提案レイアウトも独立型としてコンパイルしたが、アプリへ組み込んだ最終容量は未測定。ヒープ管理情報は特記しない限り含まない。

| 型 | バイト |
|---|---:|
| UiData | 1,256 |
| LogBrowserView / DatasetView | 464 / 472 |
| AppMapResources / AppLogResources | 696 / 1,160 |
| UiScreenResources | 256 |
| ReturnMessage / AppNotification | 584 / 816 |
| map::FrameInfo / map::Transfer | 72 / 560 |
| FatFs FIL / LogFile | 4,136 / 4,140 |
| LogReader / LogWriter | 4,688 / 6,640 |
| PlaceLookup / StorageScreenResources | 2,576 / 5,072 |
| LogExporter | 11,384 |

FILには現行SDKのファイルごとのキャッシュが含まれる。小さなハンドルとして計算しない。

## 1. ログの地図→文字でUI画像を解放する

対象: `task/ui/UiModel.cpp`のupdateContent / copyData、`map/MapFrameReceiver.h`。

Storageの区域画像はVによる文字表示への切替で解放されるが、UI境界画像はsetScreenかデータセット世代変更まで残る。同じLogPoint画面内の遷移も検出してclearする。対象点、再生位置、10件のレコードキャッシュは残す。切替後はacceptsMapが遅れた転送を拒否する。

文字表示中に画像2枚分12,120バイト、前回実機のallocator込みで12,152バイト削減できる。地図の生成中の最大使用量は減らない。地図に戻る際は現行でも区域画像を取得し直すため、この解放でSD読出し回数は増えない。消灯中にも解放できるが、復帰時に旧画像を見せるかは先に決める。

## 2. 索引検証の未使用出力領域をなくす

対象: `task/storage/dataset/DatasetIndex.cpp`のOutput。

コンストラクターは比較モードでも書込み用Fileと4KiBバッファを確保し、その後に比較用Sourceを確保する。しかし比較時のwrite / seek / finishはSourceだけを使う。

通常出力と比較出力を別状態にし、比較時はSourceだけを構築する。通常出力のCRC計算に必要なバッファは維持する。未使用File 4,148バイトとバッファ4,096バイト、計8,244バイト＋確保管理情報を検証中に削減できる。照合内容やI/O回数を変える必要はない。

## 3. Storageの返送領域をUnion化する

対象: `StorageTask.h`のpending_return_ / completion_、StorageTask.cppのrun。

現在は584バイトの戻り値と816バイトの通知を別々に保持する。runはhas_return_中にジョブを進めず、has_completion_中に次の通常要求を受け付けない。結果がキューへコピーされた後はStorage内の作成領域を再利用できる。

Idle / SyncReturn / Completionのタグ付き816バイト領域へ統合し、静的領域を約584バイト削減する候補となる。キューが満杯の間は内容を保持する契約を維持する。実装時は同期結果・通知の詰まり、USB完了、ログ保存エラーを含めて同時保持がないことを検証する。

## 4. USBの選択→変換で既存固定領域を使う

対象: PlaceLookup、LogWriter、StorageScreenResources、exporter_、`task/storage/UsbExport.cpp`。

USB/GPSは起動時に決まり、切替は再起動を伴う。現在はUSB中もGPS側固定領域が残り、その外へ11,384バイトのLogExporterを動的確保する。

```text
Storageのモード領域
  GPS: PlaceLookup + LogWriter + StorageScreenResources
  USB: 段階別Union
         選択中: LogReader
         変換中: LogExporter
```

独立レイアウト試作ではGPS側14,288バイト、USB側の最大11,384バイト、外側Unionは14,288バイトだった。GPS側の常駐量を大幅に増やさず、USB変換中の約11KiBの動的確保を固定領域へ移せる見込み。

選択名・形式を共通の小さな状態へコピー→一覧の未完了結果を回収→LogReader終了→同じ領域へExporter構築→変換・close成功→Exporter破棄→必要時にLogReaderを再構築、という手順にする。close失敗中はExporterを残す。PCとローカルFatFsの所有権切替も維持する。

現在のUSB経路にもlog_writer_のsnapshotやReaderへwriterを渡す箇所があるため、空状態またはnullptrへ分離する。LogReaderとExporterだけをUnion化するとGPS中の常駐量が増えるので、起動モードによる外側の分離も必要。複数の処理にまたがるため難度は中〜高。

## 5. UiDataを画面内の表示内容まで分解する

対象: `UiTypes.h`、`LogReadTypes.h`、`ScreenGroup.h`。

現在のページUnion外には、起動チェック一覧、地名2行、対応Fixと区域コードが常駐する。ログ一覧6件とポイントのFix・Summaryも同居する。

実GPS・設定・記録・Storage状態・起動完了/メンテナンスフラグは共通に残し、表示詳細をBoot、Live/Map、ログ一覧、ログ選択/ポイント、Datasetのタグ付き領域に分ける。ログの地図と地名は同時に必要なので同じ分岐へ置く。

戻るための選択名・ページ位置等は少量の共通コンテキストへ分離する。現在はLogDetailからLogsへ戻ると保存済み一覧を表示するため、一覧領域を潰すなら、戻る際はアンカーで一覧を再取得する手順へ変える。Appが起動後にも参照する起動状態を表示用チェック表と混同しない。

必要データのレイアウト試作はUiData 1,256→992バイト。1コピー264バイト、App・UiModel・UI受信キューの3コピーで約792バイトの静的削減が見込める。最終的なタグ・保持コンテキストで変わる。スタック上のコピーも小さくなるが、予約スタックを減らさない限り空きヒープ増加には数えない。

ログだけをUnion化しても、外側の最大要素はDatasetView 472バイトなのでUiDataは縮まらない。内側と外側を同時に評価する必要がある。

## 6. 地図の境界線を転送行単位で生成する

対象: MapBuildJob、BoundaryExtractor、App/UIの転送契約。

現行はStorageに境界画像6,060バイトを作って8行ずつ転送する。区域画像をSessionが保持するので、ReadMapRowsで必要行だけを生成し、既存Transferの480バイトへ直接出力できる。

元画像の読出し・検査完了を通知→行要求で生成→UIで全行受信後Commitという手順にする。途中失敗時はUIの未完成画像を破棄する。完成通知の意味と抽出関数の出力範囲を整理する必要がある。Galuchat変更やSD再読出しは不要。

生成中の最大使用量を6,060バイト（前回のallocator込み6,076バイト）削減し、更新ごとの確保をなくせる見込み。旧画像を表示したまま新画像を受信するUIの2枚は維持する。

## 7. 小規模な整理

| 対象 | 案 | 削減目安 |
|---|---|---:|
| AppMapResources | infoとtransfer.infoの重複をなくす。旧表示用anchorは残す | 静的72バイト |
| Appのlog_control_ | UiAction全体ではなくaction_idとLogActionを保持 | 静的約64バイト |
| PlaceLookupのtiming_ | 通常版は計測構造を持たず診断版だけ保持。参照口も分離 | 静的最大288バイト程度 |
| UiScreenResources | map/settings/usbをタグ付きUnion化 | 約44バイト |

UiScreenResourcesの256バイトには画像本体が含まれない。Union化だけで12KiB減るわけではない。また別画面の設定フィールドを初期値として読む箇所を、タグ確認付きアクセサーへ直す必要がある。

## 8. 固定化だけでは削減にならない部分

UIの4bitフレームは16,200バイトを起動後ずっと保持する。ローカルM5GFXには外部setBuffer APIがあり固定化できるが、同量程度の常駐RAMが必要。RendererはUIタスクのローカル変数なので、配列をそのままメンバー追加して8KiBのUIスタックへ載せてはいけない。所有者を静的寿命へ移す必要がある。

タスクもxTaskCreateStaticへ移せるが、予約スタック量自体は減らない。キューは既に静的確保済み。

ObservedFileReaderの索引ReaderとマップReaderは同時に存在する。マップ16KiB＋索引4KiB＋FIL2個で約28,752バイト必要となり、単一バッファでは共用できない。一律に固定化すると未使用時も占有するため、他のStorage作業との共用設計が先となる。

Wordbookのvector/stringはデータ依存の長さを持つ。固定化のために新しい上限を導入して正当なデータセットを拒否しない。索引と辞書のReader、トークン対応表には同時使用があり、すべてを重ねられるわけではない。

## 推奨順序

最初はUIの地図→文字での解放、索引比較の未使用確保除去、Storage返送領域の統合、重複メタデータの整理。その次にUSBのモード/段階別共用、UiDataのページ再分割を行う。地図処理中の余裕を優先するなら、行単位の境界生成を前へ繰り上げる。

各効果は異なる場面の値で、単純に足して通常地図の空き増加として扱わない。128×128のコード面キャッシュ、表示中の区域画像、記録中のLogWriterは同時に必要なので重ねない。今回行ったのはコード読解と型レイアウトの検証であり、改修後の動作・速度・実機メモリ測定は未実施である。
