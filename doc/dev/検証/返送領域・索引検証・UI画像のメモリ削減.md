# 返送領域・索引検証・UI画像のメモリ削減

実施日: 2026-10-26

## 変更範囲

Storageの返送領域統合、索引の比較専用経路の未使用確保除去、ログの地図表示から文字表示へ切り替える際のUI画像解放を実装した。他のUnion候補、行単位の境界生成、USBエクスポーターの固定化、消灯時のUI画像解放は今回含めていない。Galuchatライブラリ、記録形式、キュー数・容量・メッセージ形式は変更していない。

`StorageReplies`はReturnMessageとAppNotificationをタグ付きUnionで所有する。Idle、同期結果待ち、完了通知待ちを排他にし、キューへコピーできるまで内容を保持する。キューに投入済みの値は独立したコピーなので、その後は同じ作成領域を次の結果に使える。同期結果の未送信中はジョブを進めず、完了通知の未送信中は次の通常要求を受け付けない。

索引のOutputは比較モードでSourceだけを構築する。書込みモードのFileとバッファは通常出力時だけ確保する。照合順序、読出し、CRC判定、原データとの比較内容は維持する。

UIは同じLogPoint画面内でも、表示内容が地図から文字へ変わるとMapFrameReceiverの2枚を解放する。選択点とレコードキャッシュは残す。遅れて届く行とCommitは従来の表示モード検査で拒否する。地図に戻ったら新しい全行の受信後に表示する。Storageのラベル画像は現行でも文字切替時に解放されるため、SDから地図を取得する回数は増えない。

## ホスト検証

以下を警告エラー化・UBSan・標準ライブラリ境界検査付きで実施し、成功した。

- `tests/run_native.py`: 新規の返送領域試験で、結果キュー1件・通知キュー8件の満杯時の保持、異なる種別の送信抑制、投入済み値の独立性、100回のメンバー切替を検証。UIでは2枚の地図バッファと転送途中の状態を作り、V切替後の解放、遅延転送拒否、選択点保持、地図への復帰を確認。
- `tests/run_logger_app.py`: 実Appの記録・閲覧・履歴地図・再生・取消・画面資源切替。
- `tests/run_usb_export_lifecycle.py`: 実USB変換処理の受付、確保失敗、close失敗時の保持、再公開。
- `tests/run_dataset_index.py`へN03-20260101の8192/10000マップとUTF-8 Wordbookを入力: 実データと人工データの生成、読取り専用の全体／部分照合、CRCが正しい内容不一致の検出、再生成、失敗時の復旧。

索引試験はI/O回数を検査するため、試験ビルドで`REVERSEGEOPUTER_DIAGNOSTICS=1`を指定するよう修正した。通常ファームの診断設定は変えていない。

## 静的RAMとビルド

| 項目 | 変更前 | 変更後 | 差 |
|---|---:|---:|---:|
| 通常版の静的RAM | 68,096 B | 67,520 B | −576 B |
| Flash使用量 | 1,220,937 B | 1,221,245 B | ＋308 B |

ESP32-S3でReturnMessageは584 B、AppNotificationは816 B。新しいStorageRepliesはタグ・アラインメント込み824 Bとなった。単純な584 B削減の見積りに対し、最終ビルドの静的RAM削減は576 Bだった。

## 実機の比較方法

対象MAC `70:af:09:df:46:d0`、SD FAT32、実機の選択済みデータセット02（162チャンク）。SPI設定25MHz、実クロック20MHz。同じSDカード・同じ計測手順で、変更前後をそれぞれ実行した。

`tests/performance/prepare_memory_cleanup_benchmark.py`で隔離した計測版を生成する。通常のApp・Storage・UIの経路を用い、実GPSの初回地名検索後、仮想座標で地図・キャッシュミス・倍率変更・ログ地図・文字表示・メインへの退出を順に操作する。その後、選択済みデータセットの原データ突合による索引検証を3回実行する。索引の再生成、実ログ書込み、NVS設定保存は行わない。異常時の自動データセット解除によるNVS書込みも計測版では抑止する。

比較モードのOutput構築直前と直後を同じ位置で測り、同一試行内の空きヒープ差から確保量を求めた。`min_boot`は起動後の最低空きで、処理ごとにリセットした値ではない。処理段階のスナップショットを、処理全体の最大使用量と混同しない。

## メモリ実測結果

| 項目 | 変更前 | 変更後 |
|---|---:|---:|
| 索引比較準備時のヒープ消費 | 16,628 B | 8,352 B |
| ログを文字表示へ切替後の空き | 160,184 B | 172,908 B |
| メインへ退出後の空き | 172,336 B | 172,908 B |
| 全測定中の最低空きヒープ | 50,400 B | 50,772 B |

索引比較準備時は3回とも同じ確保量で、8,276 B削減した。型の実測によるFile 4,148 Bとバッファ4,096 Bの計8,244 Bに、allocatorの管理・整列の差が加わった結果である。比較に使うSourceの確保は維持する。

文字表示時とメイン退出後の空きの差は、変更前12,152 B、変更後0 Bだった。これによりUI境界画像2枚が文字表示時点で解放されたことを確認した。文字切替時の前後差12,724 Bには、静的RAM削減等による基準値の差572 Bも含まれる。UI画像の解放による効果は12,152 Bと区別する。

空きの基準値や最低値にはNMEA受信、時点ごとの一時確保等による数百バイトの変動がある。地図を表示している間は必要な画像を維持するため、今回の変更で地図生成中の使用量が12KiB減るわけではない。

## 処理時間の実測結果

索引検証はStorageが記録した、メタデータ読出しから原データとの突合までの時間を使う。

| 試行 | 変更前 | 変更後 |
|---|---:|---:|
| 1回目 | 19,747 ms | 19,711 ms |
| 2回目 | 18,528 ms | 18,509 ms |
| 3回目 | 18,526 ms | 18,520 ms |
| 中央値 | 18,528 ms | 18,520 ms |

中央値の差は−8 ms（約−0.04%）。3試行の範囲では処理時間はほぼ同じで、速度改善があったとは評価しない。メモリ削減に伴う目立った悪化は確認されなかった。

地図の読出し経路の記録値は次のとおり。境界抽出とUI転送を含む全描画時間ではない。初期座標はその起動時の実GPSから取得するため、前後で完全に同一ではなく、各値は1回ずつの確認となる。

| 読出し | 変更前 | 変更後 |
|---|---:|---:|
| 通常地図1/1初回 | 124 ms | 125 ms |
| 仮想移動後 | 125 ms | 124 ms |
| 帰還後 | 126 ms | 124 ms |
| 1/2 | 203 ms | 204 ms |
| 1/4 | 266 ms | 270 ms |
| ログ地図初回 | 262 ms | 260 ms |
| ログ地図移動後 | 269 ms | 265 ms |

画面切替の待ち時間は独立した多数回の遅延測定をしていない。新たなI/Oは加えておらず、自動操作の全段階は前後とも正常完了した。
