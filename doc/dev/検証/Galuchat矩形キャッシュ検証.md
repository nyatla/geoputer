# Galuchat矩形キャッシュ検証

検証日: 2026-10-15  
対象: GeoPuterのCachedMapReader、PlaceLookup、StorageTask  
構成: Cardputer ADV、Mesh Kit、FAT32 SD、Galuchat C++ Reader 0.5.2

本書は矩形キャッシュ導入時の検証記録である。2026-10-16に追加した地名キャッシュと、矩形・地名の両ヒット時にSDを読まない動作の検証は[WordBook地名キャッシュ検証](WordBook地名キャッシュ検証.md)を参照する。

## 1. 検証目的

点検索を128×128・32bitの矩形キャッシュで包んだ場合に、区域コードと地名結果を維持できること、範囲内の検索で地図ファイルの読出しを省けること、再構成に失敗した画像を利用しないことを確認する。

## 2. 実装前のSDK確認

行政区域N03-20260101のunitInv=1000と、統合データのunitInv=10000を使用した。習志野市庁舎、皇居付近、区域未設定の地点、負座標を中心とする128×128の矩形について、中心・各辺・角を含む各324点、合計648点でSDKの点検索と矩形画像のコードが一致した。

別途、同じ範囲に異なる非ゼロコードを持つ地図を2枚重ねた小さな検証データを作成した。この場合、SDKの点検索は先のコード1、標準の矩形読出しは後のコード2を返した。キャッシュの書込アダプターでは先の非ゼロ値を保持し、点検索の結果に合わせる。SDKのヘッダ自体は変更しない。

## 3. 自動テスト

次のコマンドで検証する。

```bash
python3 tests/run_native.py
python3 tests/run_place_files.py <mapset.glc> <names.sjis.giswordbook>
```

ファイル検証には、同じデータセットの地図とShift_JIS辞書を指定する。今回使用した組はN03-20260101-grid-4096-1000とN03-20260101.sjis.giswordbook、およびgis-estat-integrated-grid-8192-10000とgis-estat-integrated.sjis.giswordbookである。

| 検証内容 | 結果 |
|---|---|
| 行政区域版・統合版の各324点でキャッシュと元の点検索を比較 | 一致 |
| 原点を含み、原点+128を含まない境界判定 | 成功 |
| X/Yの解像度、画像の行方向、負座標の丸め | 成功 |
| ヒット時に地図ReaderFactoryのcreateを呼ばない | 成功 |
| コード0の再利用、初回確保64KiB、再構成時のバッファ再利用 | 成功 |
| 地図重なりの先の非ゼロ値優先、0の透過 | 成功 |
| UINT32_MAXの保持、32bit超過の拒否 | 成功 |
| 非ゼロの画素を書いた後の読込失敗、無効化、再読込による回復 | 成功 |
| データセット閉鎖時のキャッシュ解放 | 成功 |
| Shift_JIS地名、ファイル不足・重複・破損・修復後の再読込 | 成功 |

## 4. 実機の起動確認

PlatformIOのcardputer-adv環境でビルドし、Cardputerへ書込み、書込内容のハッシュ照合が成功した。固定RAM使用量は38,000バイト、プログラム領域使用量は1,479,173バイトである。64KiBの画像は最初の地名検索で動的に確保する。

実機ではBootからLive Placeへ遷移し、FAT32マウント、NVS設定復元、データセット番号01のReader準備が成功した。最初の起動はGPSがNO FIXだったが、測位回復後の再確認でキャッシュ生成と後続のヒットを確認できた。

| 検索 | キャッシュ状態 | 画像容量 | 累計ミス / 再構成 | 検索全体の所要時間 |
|---|---|---:|---|---:|
| 初回 | MISS | 65,536バイト | 1 / 1 | 1,907,391μs |
| 2回目 | HIT | 65,536バイト | 1 / 1 | 79,144μs |
| 3回目 | HIT | 65,536バイト | 1 / 1 | 78,922μs |

3回とも区域コード635、地名は千葉県／習志野市だった。キャッシュの原点は変わらず、再構成回数は1のまま、ヒット回数だけが0→1→2へ増加した。GPS受信は継続し、観測中に異常終了はなかった。

| 実機のメモリ指標 | Reader準備後・画像確保前 | キャッシュ検索完了後 |
|---|---:|---:|
| 空きヒープ | 217,588バイト | 151,768バイト（約148KiB） |
| 起動以降の最小空きヒープ | 207,984バイト | 146,392バイト（約143KiB） |
| 最大連続空き領域 | 204,788バイト | 139,252バイト |

検索後の3指標は3回とも同じ値であり、この短時間の観測では検索ごとの追加減少はなかった。所要時間とメモリ値は今回のSD・データセット・検索地点による測定結果であり、全地点・全データセットで同じ値となることは保証しない。実機での移動による範囲外再構成は未実施で、境界と再構成動作は自動テストで確認した。

## 5. 実機の検索確認方法

有効Fix取得後にLive Placeを表示し、シリアルログの[CACHE]を確認する。最初はMISS、画像容量65,536バイト、再構成1回となり、同じ矩形内の後続要求はHITとなる。矩形はミス時の取得点を中心としていることを確認する。画面消灯中は新しい検索を開始しないため、必要に応じてキーでLive Placeへ復帰する。

[GIS]のheap、min_heap、largestはバイト単位の空きヒープ、起動以降の最小空きヒープ、最大連続空き領域である。[CACHE]のelapsed_usはWordBook読出しと文字コード変換を含む検索全体の時間であり、矩形再構成だけの時間とは区別する。


## 6. 地名の更新とアクセス表示

Live Placeの再検索開始で地名を消去せず、旧地名と対応座標を保持し、完了結果で3行と座標を一緒に置き換える。GPS喪失時は旧地名・座標・アクセス要求IDを消去し、WAIT GPS FIXを16×16ドットで表示する。右上には8×8ドットのASCIIでC（キャッシュ）／R（再読出し）を置き、文字自体を点灯する。

ホストテストで地名・対応座標の保持と一括更新、エラー表示、GPS喪失時の消去、古い要求の開始通知の除外を確認した。UIでは短いアクセスと開始・完了を統合した更新の150ms点灯、長い処理中の点灯維持、同一要求での再点灯防止、期限切れによる再描画、時刻周回、GPS喪失時の即時消灯を確認した。実ファイル検証では参照方式の事前判定と実際のキャッシュ範囲が一致し、その判定で画像確保・ファイル参照・統計更新が発生しないことを確認した。

実機の表示確認では、初回はRの黄、範囲内の次回検索はCの緑で確認する。どちらの点灯でも、既存地名と座標が検索中に消えないことを確認する。GPS喪失時はWAIT GPS FIXの各文字が16×16セルで描画され、ランプが両方消灯することを確認する。

表示更新版のファームウェアはPlatformIOでビルドし、Cardputerへ書き込んで4領域のハッシュ照合が成功した。固定RAMは38,296バイト、プログラム領域は1,480,249バイトである。再起動後はBootの6項目が成功し、実座標から千葉県／習志野市、区域コード635を取得した。初回MISSは1,908,698μs、後続HITは80,592μsと80,557μsで、矩形再構成は1回のままだった。18秒の取得ログでNMEA 255行、解析拒否0、異常終了なしを確認した。LCD上のランプとちらつきの目視確認は未実施である。
