# 地図Sessionと区域画像保持の検証

実施日: 2026-10-26

## 対象

32bitの区域コード画像を地図表示中のMapSessionが所有し、生成ジョブが借用する方式を検証する。通常地図とログ地図には独立したSessionを用意し、大きな配列は同時保持しない。128×128の共通コード面キャッシュとWordbook LRUは従来どおり使用する。

新しい範囲の読出しは保持配列を上書きする。区域だけが変わった場合は、同じ生成中心の画像から境界線を再抽出し、SDを読まない。ReleaseMapはジョブと小さな境界画像を解放し、CloseMapSessionは元の区域コード画像を解放する。

## ホスト検証

以下の試験はすべて成功した。C++の試験は警告をエラーとして扱い、UBSanと標準ライブラリの境界検査を有効にした。

- `python3 tests/run_native.py`: 画像処理、Sessionを跨ぐ再利用の拒否、Release後の区域画像保持、再描画時の同一ポインタ使用、区域0の扱い。
- `python3 tests/run_logger_app.py`: App・UIのログ閲覧、点送り、履歴座標、再生停止、記録との共存。
- `python3 tests/run_map_scale.py`: 実Appの倍率変更、取消・旧結果の拒否、同一範囲の区域変更、離脱時の元画像解放。
- `python3 tests/run_map_files.py <estatのGLC> <UTF-8 Wordbook>`: 実ファイルで次の地図を同一配列へ読出し、区域再描画でSDアクセスが増えないこと、倍率1/2・1/4、既存128キャッシュの維持。
- `tools/render_log_browser.py`: 英語・日本語各28場面の画像生成。
- `tools/render_map_view.py --scales 1 2 4`: 地図24場面の画像生成。

GaluchatのCore・SDK・アプリ内ライブラリには変更を加えていない。

## 実機測定方法

`tests/performance/prepare_map_session_benchmark.py`で通常版から独立した計測用ビルドを生成する。NVSの保存先・設定・実ログを変更せず、仮想座標を用いて通常Appの地図生成・地名検索・フレーム転送経路を操作する。

最初の地名検索完了後に測定を開始し、通常地図の保持、区域のみの再描画、緯度0.02度移動による共通コードキャッシュの再構成、元位置への復帰、倍率1/2・1/4、ログ地図への切替、そのキャッシュミス、文字表示への復帰、メインへの退出を順に測る。実機GPSから取得した基準点以外は仮想移動であり、歩行・走行の試験ではない。

`heap`はその時点の空き8bitヒープ、`largest`は最大連続空き領域。`min_boot`は起動からの最小値であり、各処理でリセットした最低値ではない。`bytes`はStorage段階では元画像の保持量、ベンチ段階では段階番号を表す。通常版へ自動操作コードは含めない。

## 実機結果

対象MAC `70:af:09:df:46:d0`のCardputer ADV、SD FAT32、データセット01（162チャンク）、習志野付近の実座標を基準に測定した。SPI設定25MHzに対し実クロックは20MHz。9段階すべて完了し、計測開始から12.821秒で`[SESSION-BENCH-DONE] OK`となった。段階間の待機・UI転送を含む時間であり、地図処理時間そのものとは異なる。

| 段階 | 空きヒープ（バイト） | 最大連続空き（バイト） |
|---|---:|---:|
| 初回地名検索後・地図を開く前 | 172,344 | 159,732 |
| 通常地図・区域のみ再描画後 | 80,496 | 56,308 |
| 地名キャッシュミス＋地図読直し後 | 80,496 | 56,308 |
| 元位置への復帰後 | 80,496 | 56,308 |
| 倍率1/2 | 80,496 | 56,308 |
| 倍率1/4 | 80,496 | 56,308 |
| ログ地図の初回表示 | 86,572 | 67,572 |
| ログ地図でキャッシュミス＋読直し後 | 80,496 | 56,308 |
| ログ文字表示へ戻る | 160,192 | 86,004 |
| メインへ退出後 | 172,344 | 159,732 |

全試験中の最低空きヒープは50,208バイト（約49.0KiB）。元画像保持中の地名キャッシュ・Wordbookミスで50,964バイトまで下がり、その後の地図読出しで50,208バイトとなった。最低値はallocatorの起動後low-water markであり、最大連続空き領域の最低値を表すものではない。

保持する元画像は79,680バイト（240×83×4、約77.8KiB）。通常地図・ログ地図ともこの量で、倍率変更でも増加しなかった。通常地図での移動・帰還・倍率変更、およびログ地図での移動の計5回が`source-reused`を通った。通常地図からログ地図へ切り替える際は旧Sessionの`session-closed`を確認してから次の`source-allocated`へ進んだ。

区域のみの変更では`render-done-retained`→UI転送→`released-retained`となり、間に地図読出し・元画像再確保は発生しなかった。保持中のSearchPlaceも完了し、共通128キャッシュのミス・Wordbookのミスから正常に復帰した。

退出後の空きヒープと最大連続空き領域は測定開始前と一致した。文字表示へ戻った段階では元画像は解放済みだが、同じログ画面のUI境界画像2枚（allocator込み12,152バイト）はまだ保持され、メインへの退出時に解放される。初回表示・更新後でUIの受信バッファが1枚／2枚となるため、ログ初回表示だけ6,076バイト多く空いている。

計測版のSHA-256は`9e34e5c5090009e570ff3d0761c4e2a3bfcde9df9f6215382f1fca836f0e9d37`。生ログと通常版バイナリはローカルの`.pio/map-session-checks/`へ保存する。

この結果は上記の座標・データセットでの実測であり、赤道付近・異なる格子比・同時に実ログを保存し続ける長時間運用は未測定。記録との機能的な共存はホスト試験で確認した。

測定後に上記SHA-256の通常版を書き戻し、書込みのhash検証・SD FAT32・データセットOPEN OK・GPS FIX・LivePlace起動を確認した。自動計測コードは含まれない。今回の実機操作は自動プローブによるもので、物理キーからのログファイル選択・リプレイの目視確認は別途行う。
