# ログ統計追加前後のメモリ比較

実施日: 2026-10-27。対象はログプロパティ・統計表示の追加前後。変更前は `.pio/log-statistics-before/` の保存ソースと通常ELF、変更後は書込み済みファーム `f3663753b042ae9ed978ceaa29cfa5e05d67ce69da1b8161b27f1816d623da51` と対応するソースである。

## 結論

静的データRAMは95,064→95,512 B、増加は448 B（0.438 KiB）。UIキューの120 Bもこの中に含まれ、別枠のヒープ増加ではない。起動直後に地名キャッシュを温めたメイン画面では、ヒープ占有量は前後とも160,876 Bで一致した。

地図の生成を含む全体ピークもほぼ同じだった。1ms採取で観測した最大ヒープ占有量は266,956→266,924 B。allocatorの起動後低水位から求めた占有量は267,020→266,996 Bであり、追加機能による大きなヒープ増加は観測していない。空き量が約400 B減る主因は、静的RAMがヒープの容量を448 B使ったことである。

今回の条件では、消費の山は地図の生成・保持で、929点のログ統計ではなかった。メインへ戻った後の使用量は、各起動の2・3周目で一致した。2周目から3周目へ増え続ける状態は観測しなかった。

## 1. 計測条件と用語

Cardputer ADV、ESP32-S3 240MHz、PSRAMなし。同じFAT32 SD・選択済みデータセット02（162チャンク）を使用した。現在地は計測版内だけで北緯35.681641、東経140.027194に固定し、GPS受信は続けた。ログ地図の共通試験は同じ仮想点で行い、実ファイルの比較には `20261026_105455_0.gps.dat`（929点）を前後とも読み込んだ。ログ書込み・削除、設定の保存、索引再生成は行わない。

変更前→変更後→変更前→変更後の順で独立起動を各2回、各起動で3周した。表示が落ち着いてからの比較は2・3周目、前後各4サンプルを使用する。初周はライブラリや地名検索の初回使用による変化があるため、定常状態と分ける。

共通の経路はメイン→地図1/1→地図1/4→ログ地図→文字表示→一覧→実ログの点表示→メイン。変更後だけ、プロパティと統計を追加した。各保持状態で約1秒待機する。統計は6回とも929点・error=0で終了した。

計測用に同じ採取コードを組み込み、2,048 Bスタックの採取タスクを1つだけ追加して1msごとに観測した。既存のReader／地図段階の採取点でも観測する。追加の静的領域は前後とも472 Bで、比較版の静的RAMは95,536／95,984 Bとなる。採取タスクのTCB・スタック等はヒープを使う。以下のヒープ絶対値はこの共通の計測負荷を含み、通常版の値へ根拠なく補正しない。

採取対象は `MALLOC_CAP_INTERNAL | MALLOC_CAP_8BIT`。

- **容量**: `heap_caps_get_total_size` の値。
- **空き**: `heap_caps_get_info().total_free_bytes`。
- **占有量**: 容量−空き。確保データのほかallocatorの管理・配置分も含む。
- **割当済み量**: APIの `total_allocated_bytes`。上の占有量と同じ数値ではない。
- **最大連続領域**: `largest_free_block`。空きの合計が多くても、この値より大きな単一確保が可能とは限らない。
- **起動後低水位**: allocatorが保持する `minimum_free_bytes`。区間ごとにはリセットされず、複数のヒープ領域の低水位を含むため、1ms観測の瞬間値とは区別する。

静的RAMのPlatformIO値は `.dram0.data + .dram0.bss`。SDKのヒープ容量は複数の実機メモリ領域を集計するため、PlatformIO表示の320 KiBから静的RAMを引いて空き量を推定しない。

## 4. 一時ピークと最大連続領域

| 指標 | 変更前 B | 変更後 B |
|---|---:|---:|
| 1ms観測の最大占有量 | 266,956 | 266,924 |
| 1ms観測の最低空き量 | 53,528 | 53,112 |
| allocatorの起動後最低空き量 | 53,464 | 53,040 |
| 上記低水位から求めた占有量 | 267,020 | 266,996 |
| 全区間の最小観測・最大連続領域 | 38,900 | 38,900 |

現在の計測版は、最も空きが少ない時に約51.8 KiB、地図保持で約77.4 KiB、メインで約155.2 KiBが空いていた。全体の山は地図読出し・生成である。1ms採取で捕捉できない短時間の確保もあるため、allocatorの低水位も併記した。

地図保持中の最大連続領域は、通常地図では変更前57,332–65,524 B、変更後57,332–59,380 Bだった。最初の前後比較では6,144 Bの差があったが、2回目の通常地図では両方57,332 Bになった。割当順序・配置による変動を含み、今回の2起動ずつの比較では再現性のある断片化悪化は確認できない。地図から戻ると両方147,444 Bに戻った。空き総量だけで単一64 KiBの追加確保を判断すべきではない。

文字表示中の地名再取得などでは数百バイトのピーク差もあった。全体のピークが同程度だからといって、すべての瞬間の確保量が完全に一致するとは扱わない。

## 5. 統計処理と消費の大きな領域

変更後のプロパティ、点表示、統計結果保持は、定常時の占有量がいずれも161,152–161,164 Bで一致した。統計処理中の観測占有量は最大161,348 B、空きは最低158,688 B、最大連続領域は最低147,444 Bだった。929点の集計は6回とも成功し、新しい全件配列のような増大は見られなかった。

統計は固定長64 Bの結果を既存返送unionへ入れ、8点256 Bのバッチを既存320 B領域で処理する。UI側の結果保持も上記の静的増加に含まれる。[先の1千・1万・10万点の試験](ログプロパティと統計表示の検証.md)でも、統計付き各2回の最低空きは157,264–157,508 Bの範囲だった。この試験は採取コードや専用FIL等の構成が異なるため、今回の絶対値と直接比較しない。件数に比例する確保がないことの補足として扱う。

今回、地図保持とメインの占有差は前後とも79,696 Bだった。Storageの保持コード画像は79,680 Bとログに記録され、allocator込みの差と一致する。1/1と1/4で保持量は同じだった。この座標・データセットでの結果であり、他の緯度・形状へ一律には当てはめない。

他の主な領域も今回の変更で増えていない。

- 地名検索用の128×128×uint32キャッシュは64 KiB。Storageで動的に確保され、画面外でも保持する。
- UIの境界画像2枚は6,060 B×2、画面用4bitバッファは16,204 B。UiTaskが内包する静的領域で、上の静的RAMへ既に含む。
- 64点の記録リング、10点のログ閲覧バッファ、キューと返送unionは既存領域を使う。

今回の追加に限れば、大きなヒープ削減を必要とする増加は起きていない。さらにピークを削るなら、数百Bの統計状態より、約80 KiBの保持区域画像と生成中の一時領域を調べる方が効果は大きい。

## 6. 再現手順・資料・復旧

`tests/performance/prepare_heap_comparison.py before` と `after` で独立した計測ソースを準備する。比較元は保存済み変更前ソースと現在のapplication。共通のHeapComparisonProbeで採取し、同じ画面遷移を実行する。今回の期間中、applicationの製品コードは変更していない。
